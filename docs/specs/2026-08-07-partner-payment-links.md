# Платёжные ссылки в кабинете партнёра

**Дата:** 2026-08-07
**Статус:** дизайн согласован, к реализации

## Зачем

У B2B-агентов сейчас единственный способ выставить клиенту счёт — Telegram-бот
(`feature/separation-of-roles`, внешняя разработка). Партнёрам, которые уже сидят
в реферальном кабинете (`/ref/<token>`), нужен тот же сценарий без бота: ввёл сумму
в рублях → получил ссылку на оплату → отдал клиенту. Оплата сама превращается
в сделку CalcCRM с привязкой к партнёру.

Возможность выдаётся **точечно** — не всем партнёрам.

## Что НЕ входит

- Направления кроме `RUB → THB` (USDT-плечо, `RUB → USDT`) — позже, если попросят.
- Партнёр НЕ управляет курсом: он задаёт только сумму, курс наш.
- Роли «руководитель / агент» как в боте — в кабинете один партнёр = одна учётка.
- Изменения в самом Telegram-боте.

## 1. Доступ

Новая колонка `referrers.can_create_links BOOLEAN DEFAULT FALSE`
(через `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` в блоке миграций, как остальные).

- В карточке партнёра в CRM — чекбокс «Может создавать платёжные ссылки».
- В кабинете блок рисуется по флагу из `/api/ref/<token>/stats`.
- **Флаг проверяется на сервере в каждом эндпоинте ссылок**, не только в UI.

**Требование безопасности:** включать флаг можно только партнёру с
`auth_mode='telegram'`. В режиме `link` `ref_session_authorized()` пускает любого,
у кого есть URL с токеном (app.py:6943) — а тут речь о создании платежей от нашего
имени. Попытка включить флаг партнёру в link-режиме → 400 с явным текстом.

## 2. Модель данных

Таблица `partner_links` — ссылка как заявка:

| Поле | Тип | Смысл |
|---|---|---|
| `id` | int PK | |
| `referrer_id` | FK referrers, index | владелец |
| `order_id` | str(64) unique, index | `GRP-<referrer_id>-<ts>` — он же `order_transaction_id` в Доверке |
| `amount_rub` | float | что вводит партнёр |
| `quoted_thb` | float | сколько получит клиент (снапшот на момент создания) |
| `quoted_rate` | float | итоговый курс RUB→THB |
| `quoted_usdt` | float | USDT-плечо расчёта |
| `profit_margin_used` | float | маржа, с которой считали (база + markup партнёра) |
| `markup_percent` | float | наценка партнёра, если `comp_model='markup'` |
| `client_name` | str(100) null | кому выставлено (опционально) |
| `client_contact` | str(100) null | @tg / телефон (опционально) |
| `provider` | str(20) | `grusha` \| `doverka` |
| `public_link` | str(512) | ссылка для клиента |
| `status` | str(20) | `pending` \| `paid` \| `expired` \| `cancelled` |
| `deal_id` | FK deals null | созданная сделка (идемпотентность) |
| `created_at` / `paid_at` / `checked_at` | datetime | |

`deal_id IS NOT NULL` — единственный признак «сделка уже создана». Любой путь
(вебхук, поллер, ручное подтверждение) обязан проверять его перед созданием.

## 3. Расчёт курса

Курс считает **только сервер**. Браузер партнёра присылает сумму, а не цифры расчёта.

`POST /api/ref/<token>/links/quote` → `{amount_rub}` →
`{thb_amount, rate, amount_rub, expires_at}`.

Внутри: `CommissionCalculator.get_level(amount_rub)` даёт базовую маржу уровня,
дальше `ExchangeCalculator.rub_to_thb(amount_rub, custom_profit_margin=base + markup)`,
где `markup` = `referrer.markup_percent` при `comp_model='markup'`, иначе `0`.
Так наценка партнёра оказывается **в курсе клиенту** — правило от 2026-08-06
(markup считается от объёма и оплачивает его клиент, нашу прибыль он не трогает).
Партнёру с `revshare` курс отдаётся стандартный, его доля считается от прибыли
сделки обычным каскадом `deal_agents`.

**Ответ урезан до публичных полей.** `/api/calculate` отдаёт всю кухню
(`profit_usdt`, комиссии, курсы закупки) — партнёру уходят только сумма, курс
и выдача. Отдельный сериализатор, не `jsonify(result)`.

Котировка живёт 15 минут (`expires_at` — для подсказки в UI). При создании ссылки
сервер **пересчитывает заново** и сохраняет свой результат: курс живой, а цифрам
из браузера мы не верим.

## 4. API кабинета

Все эндпоинты: `ref_session_authorized()` + `referrer.active` + `can_create_links`.

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/api/ref/<token>/links/quote` | котировка (см. выше) |
| POST | `/api/ref/<token>/links` | создать ссылку |
| GET | `/api/ref/<token>/links` | список партнёра, пагинация `per_page` (дефолт 20) |
| POST | `/api/ref/<token>/links/<id>/cancel` | отменить, только `pending` и только свою |

Создание идёт через существующий `/api/proxy/create-payment`
(`grusha` → fallback `doverka`), но вызывается **внутренним хелпером**, а не HTTP-хопом
в себя. В `metadata` кладём `link_id`, `ref_code`, `thb_amount`, `rate`.
Если основной провайдер лёг — ссылка создаётся через Доверку, и в ответе флаг
`fallback: true`, чтобы UI сказал «создана через резервного провайдера»
(партнёр увидит домен `merchant.doverkapay.com` и не должен пугаться).

**Лимиты:** сумма 1 000–1 000 000 ₽; не более 20 созданий в час на партнёра
и не более 5 одновременно висящих `pending` — иначе 429 с понятным текстом.

## 5. Детект оплаты

Два пути, оба идемпотентны:

1. **Вебхук** `/api/webhook/doverka` (уже есть, HMAC-подпись, app.py:7387).
   Сейчас он только шлёт сообщение в TG. Дописываем: при `status=PAID` ищем
   `partner_links.order_id == order_transaction_id` → создаём сделку.
2. **Поллер** `partner-links-poll`, фоновый тред по образцу `_tronscan_warm_loop`
   (app.py:5725), интервал 120 с, флаг `PARTNER_LINKS_POLL_ENABLED` (в тестах выключен).
   Берёт `pending`-ссылки моложе 24 ч, дёргает `GET /v1/payments/{order_id}`,
   обновляет `checked_at`. `PAID` → сделка, `EXPIRED`/`CANCELLED` → тот же статус
   у ссылки. Старше 24 ч без оплаты → `expired`.

Вебхук — быстрый путь, поллер — страховка: `callback_url` подставляется только
в прямой Doverka-ветке (app.py:7352), а основной провайдер grushab-2-b.ru наш
вебхук не зовёт.

## 6. Оплата → сделка

Создаётся **одна** сделка, поля:

- `status = pending` — деньги от клиента получены, баты ещё не выданы.
- `payin_method = spp_doverka`, `deal_type = pay_in`
- `payin_amount_rub = amount_from` (из ответа Доверки, а не из ссылки — платят иногда не ту сумму)
- `payin_amount_usdt = amount_to × 1.024` (бонус Доверки)
- `doverka_transaction_id = order_id`
- `payout_amount_thb = quoted_thb` — план выдачи, менеджер поправит фактом
- `referrer_id` партнёра + строка в `deal_agents` через `_refresh_deal_agents()`
- клиент: если `client_name` заполнено — ищем/создаём `Client` с `referrer_id`
  партнёра; иначе `client_name = "Клиент партнёра <code>"` без записи в `clients`
- `manager_name = None` — сделку подхватывает дежурный менеджер

Логику создания вынести в хелпер, общий с `POST /api/deals` (app.py:4191), чтобы
вебхук и поллер не дублировали расчёт `deal_agents` — источник истины по выплатам
партнёрам это строки `deal_agents` (решение от 2026-06-10).

**Расхождение суммы.** Если `amount_from` отличается от `amount_rub` ссылки больше
чем на 1 ₽ — сделка всё равно создаётся, но в TG-уведомление добавляется строка
«⚠️ оплачено N ₽ вместо M ₽», и `payout_amount_thb` не проставляется: пересчёт
выдачи — решение менеджера, не автомат.

**Уведомление менеджеру** (`send_telegram_notification`): партнёр, сумма, клиент,
ссылка на сделку. Для `referrer.is_test = true` — не слать (как и в остальном коде).

## 7. Кабинет

Новый блок «Ссылки на оплату» в `static/referrer/index.html`, между реф-ссылками
и выплатами, виден только при `can_create_links`:

- Форма: сумма ₽ (обязательно), имя клиента, контакт (оба опционально).
  По вводу суммы — дебаунс 500 мс → `quote` → строка «Клиент получит **N ฿**
  по курсу X». Кнопка «Создать ссылку» активна только при валидной котировке.
- Результат: готовая ссылка + кнопка «Скопировать» (переиспользуем `copyUrl()`).
- Список последних ссылок: дата, сумма ₽ → ฿, клиент, статус-бейдж,
  копирование, «Отменить» у `pending`. Пагинация тем же `renderPager()`.

Стиль — существующие классы кабинета (`ref-url`, `pager`, модалки выплат).

## 8. Тесты

- `can_create_links=false` → 403 на всех четырёх эндпоинтах.
- `auth_mode='link'` + попытка включить флаг → 400.
- Чужая ссылка: отмена/чтение по токену другого партнёра → 404.
- Котировка markup-партнёра: курс клиенту хуже стандартного ровно на его наценку;
  revshare-партнёр получает стандартный курс.
- Ответ `quote` не содержит `profit_usdt`, `commission`, `rub_usdt`, `usdt_thb`.
- Создание не верит клиентским `thb_amount`/`rate` — они игнорируются.
- Вебхук `PAID` → ровно одна сделка; повторный вебхук по тому же `order_id`
  сделку не дублирует; поллер после вебхука тоже не дублирует.
- `amount_from ≠ amount_rub` → сделка создана, `payout_amount_thb` пуст, флаг в уведомлении.
- Сделка привязана к партнёру: строка в `deal_agents` с его `comp_model`.
- Лимиты: 21-я ссылка за час → 429; 6-я висящая `pending` → 429.
- `is_test` партнёр → уведомление не уходит.

## 9. Порядок выкатки

1. Миграция колонки + таблицы, чекбокс в CRM (флаг у всех выключен — прод не меняется).
2. Эндпоинты котировки/создания + блок в кабинете, включаем одному партнёру.
3. Вебхук и поллер, проверка на реальной оплате мелкой суммой.

Пункт 3 до включения партнёрам: пока сделка не создаётся автоматически,
оплата по ссылке никак не отражается в CRM.
