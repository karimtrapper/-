# Платёжные ссылки в кабинете партнёра

**Дата:** 2026-08-07
**Статус:** дизайн согласован, к реализации

## Зачем

B2B-агенты (`A-PseudoCode-A/telegram-bot-grusha`, ветка `feature/separation-of-roles`)
выставляют клиентам счета только через Telegram-бота. Задача — дать им тот же
сценарий в вебе: ввёл сумму → получил ссылку на оплату → отдал клиенту. Оплата
превращается в сделку CalcCRM с привязкой к партнёру и начислением по его профилю.

**Пользователь — существующие агенты бота.** Реализация — своя, в CalcCRM: коннектор
и калькулятор дёргаем напрямую, кода бота не касаемся (разработка внешняя, только ТЗ).

## Что бот делает сегодня (разобрано по коду)

| Что | Как в боте | Как у нас |
|---|---|---|
| Ввод суммы | баты (`amount_outcome`), рубли считаются | ₽ и ฿ на выбор |
| Курс и комиссия | `api.exgreen.pro/api/calculate_partner`, `partner_percent: 50.0` захардкожен, комиссия в THB | `/api/calculate` в CalcCRM + модель партнёра (`revshare`/`markup`), выплата в USDT |
| Ссылка | `grushab-2-b.ru/api/payments`, `X-Provider-Name: doverkapay`, поле `webhook_url` на каждый платёж | то же, но `webhook_url` наш |
| Оплата | вебхук `/bot-webhooks/connector` → `status=PAID` → уведомление агенту и руководителю | наш вебхук → сделка в CalcCRM |
| Учёт | сделка в Битрикс **C18** (`corp.maksfin.ru`) | сделка в CalcCRM, Битрикс не трогаем |
| Инвойс | таблица `invoices` в своей Postgres | таблица `partner_links` в базе CalcCRM |

Два факта отсюда важны для реализации:

- **`webhook_url` передаётся на каждый платёж** — детект оплаты решается вебхуком,
  поллер Доверки нужен только страховкой. Наш `/api/proxy/create-payment` это поле
  сейчас не пробрасывает (whitelist, app.py:7291).
- **Вебхук коннектора не подписан.** Бот верит телу запроса на слово (`endpoints.py`,
  `connector_webhook`) — кто угодно, зная `order_id`, пришлёт «PAID». Мы так не делаем,
  см. §5.

## Что НЕ входит

- Миграция истории: старые инвойсы и баланс агентов остаются в боте, выводятся через
  бота. Кабинет считает только то, что создано в нём.
- Роли «руководитель / агент» из бота. Первая версия: один агент = один `Referrer`,
  выводит сам. Руководитель, если нужен, заводится вторым уровнем каскада `deal_agents`
  (`tier=2`) — механика уже есть и считает от остатка.
- Направления кроме `RUB → THB`; методы оплаты кроме СБП (наличные, курьер, USDT).
- Выключение бота. Он продолжает работать параллельно.

## 1. Идентичность и доступ

Агент бота = запись `Referrer` в CalcCRM. Заводится вручную в CRM (агентов десятки,
не тысячи): имя, `telegram_user_id` = его `tg_user_id`, `auth_mode='telegram'`,
модель вознаграждения (`revshare`/`markup`) и процент.

Новая колонка `referrers.can_create_links BOOLEAN DEFAULT FALSE`
(`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` в блоке миграций) + чекбокс в карточке
партнёра в CRM.

- Блок в кабинете рисуется по флагу из `/api/ref/<token>/stats`.
- **Флаг проверяется на сервере в каждом эндпоинте ссылок**, не только в UI.
- Включить флаг можно только партнёру с `auth_mode='telegram'`: в режиме `link`
  `ref_session_authorized()` пускает любого, у кого есть URL с токеном (app.py:6943),
  а тут речь о создании платежей от нашего имени. Иначе — 400 с явным текстом.

**Расхождение с ботом, которое надо принять осознанно:** за одну и ту же работу агент
получит в боте 50% через `calculate_partner` (в батах), а в кабинете — свой
`revshare`/`markup` (в USDT). Пока агент пользуется обоими, числа не совпадут.
Процент в профиле выставляем так, чтобы сойтись с его текущей моделью, либо
договариваемся, что новые заявки идут только через кабинет.

## 2. Модель данных

Таблица `partner_links`:

| Поле | Тип | Смысл |
|---|---|---|
| `id` | int PK | |
| `referrer_id` | FK referrers, index | владелец |
| `order_id` | str(64) unique, index | UUID4 — он же `order_id` коннектора и `order_transaction_id` Доверки |
| `display_name` | str(20) unique | человекочитаемый номер `AB-7`, как в боте |
| `input_currency` | str(3) | `RUB` \| `THB` — что вводил партнёр |
| `amount_rub` | float | к оплате клиентом |
| `amount_thb` | float | к выдаче клиенту |
| `quoted_rate` | float | курс на момент создания |
| `quoted_usdt` | float | USDT-плечо расчёта |
| `profit_margin_used` | float | маржа расчёта (база + markup партнёра) |
| `markup_percent` | float | наценка партнёра при `comp_model='markup'` |
| `client_name` / `client_contact` | str(100) null | опционально, для менеджера |
| `provider` | str(20) | `grusha` \| `doverka` |
| `public_link` | str(512) | ссылка для клиента |
| `status` | str(20) | `pending` \| `paid` \| `expired` \| `cancelled` |
| `deal_id` | FK deals null | созданная сделка |
| `created_at` / `paid_at` / `checked_at` | datetime | |

`order_id` — UUID4, а не предсказуемый `GRP-<id>-<ts>`: вебхук коннектора не подписан,
угадываемый идентификатор упрощает подделку.

`deal_id IS NOT NULL` — единственный признак «сделка создана». Любой путь (вебхук,
поллер, ручное подтверждение) проверяет его перед созданием.

## 3. Расчёт курса

Считает **только сервер**, браузер присылает сумму и валюту ввода.

`POST /api/ref/<token>/links/quote` → `{amount, currency}` где `currency ∈ {RUB, THB}`
→ `{amount_rub, amount_thb, rate, expires_at}`.

Внутри `/api/calculate`-логика: `scenario='rub-to-thb'`, `direction='amount'` при вводе
в рублях и `direction='target'` при вводе в батах (как в боте). Маржа:
`CommissionCalculator.get_level()` даёт базу уровня, плюс `referrer.markup_percent`
при `comp_model='markup'` — наценка партнёра оказывается **в курсе клиенту**
(правило от 2026-08-06: markup считается от объёма и платит его клиент).
Для `revshare` курс стандартный, доля считается от прибыли сделки каскадом `deal_agents`.

**Ответ урезан до публичных полей.** `/api/calculate` отдаёт `profit_usdt`, комиссии
и курсы закупки — партнёру уходят только суммы и итоговый курс. Отдельный сериализатор,
не `jsonify(result)`.

Котировка живёт 15 минут (`expires_at` — для подсказки в UI). При создании ссылки сервер
**пересчитывает заново**: курс живой, цифрам из браузера не верим.

## 4. API кабинета

Все эндпоинты: `ref_session_authorized()` + `referrer.active` + `can_create_links`.

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/api/ref/<token>/links/quote` | котировка |
| POST | `/api/ref/<token>/links` | создать ссылку |
| GET | `/api/ref/<token>/links` | свои ссылки, пагинация `per_page` (дефолт 20) |
| POST | `/api/ref/<token>/links/<id>/cancel` | отменить, только `pending` и только свою |

Создание идёт внутренним хелпером (не HTTP-хопом в себя), payload как у бота:
`amount`, `currency: RUB`, `order_id` (UUID), `merchant_id` = код партнёра,
`description = "Invoice <display_name>"`, **`webhook_url`** = наш эндпоинт,
`metadata: {link_id, ref_code}`, заголовок `X-Provider-Name: doverkapay`.
Ответ коннектора: `public_link` → `approve_url` → `/pay/<payment_id>` (тот же порядок
фоллбэков, что в боте). Если коннектор не отвечает — fallback на прямой Doverka API,
в ответе `fallback: true`, UI говорит «создана через резервного провайдера»
(клиент увидит домен `merchant.doverkapay.com`).

`webhook_url` добавляется в whitelist `/api/proxy/create-payment` **как серверное поле** —
из тела запроса оно не принимается никогда, иначе любой авторизованный сможет увести
уведомления об оплате на свой адрес.

**Лимиты:** сумма 1 000–1 000 000 ₽; не более 20 созданий в час на партнёра и не более
5 одновременно висящих `pending` — иначе 429 с понятным текстом.

## 5. Детект оплаты

**Вебхук** `POST /api/webhook/connector/<secret>` — новый эндпоинт, секрет в пути
(`CONNECTOR_WEBHOOK_SECRET`, сравнение через `hmac.compare_digest`). Коннектор подписи
не шлёт, поэтому тело запроса — только сигнал «посмотри на этот платёж», а не источник
истины: перед созданием сделки сервер сам дёргает `GET /v1/payments/{order_id}` у Доверки
и берёт статус и суммы **оттуда**. Подделанный вебхук не создаст сделку.

**Поллер** `partner-links-poll` — фоновый тред по образцу `_tronscan_warm_loop`
(app.py:5725), интервал 120 с, флаг `PARTNER_LINKS_POLL_ENABLED` (в тестах выключен).
Берёт `pending`-ссылки моложе 24 ч, дёргает тот же `GET /v1/payments/{order_id}`,
обновляет `checked_at`. `PAID` → сделка, `EXPIRED`/`CANCELLED` → тот же статус у ссылки,
старше 24 ч без оплаты → `expired`. Страховка на случай, если вебхук не долетел.

Оба пути идут через один хелпер `_settle_partner_link(link, doverka_payment)` —
идемпотентный по `link.deal_id`.

## 6. Оплата → сделка

Создаётся **одна** сделка:

- `status = pending` — деньги от клиента получены, баты ещё не выданы
- `payin_method = spp_doverka`, `deal_type = pay_in`
- `payin_amount_rub = amount_from` из ответа Доверки (а не из ссылки — платят иногда не ту сумму)
- `payin_amount_usdt = amount_to × 1.024` (бонус Доверки)
- `doverka_transaction_id = order_id`
- `payout_amount_thb = amount_thb` — план выдачи, менеджер поправит фактом
- `referrer_id` партнёра + строка в `deal_agents` через `_refresh_deal_agents()`
- клиент: при заполненном `client_name` ищем/создаём `Client` с `referrer_id` партнёра;
  иначе `client_name = "Клиент партнёра <code>"` без записи в `clients`
- `manager_name = None` — сделку подхватывает дежурный менеджер

Логику вынести в хелпер, общий с `POST /api/deals` (app.py:4191), чтобы вебхук и поллер
не дублировали расчёт `deal_agents`: источник истины по выплатам партнёрам — строки
`deal_agents` (решение от 2026-06-10).

**Расхождение суммы.** Если `amount_from` отличается от `amount_rub` больше чем на 1 ₽ —
сделка создаётся, но `payout_amount_thb` не проставляется, а в уведомление идёт строка
«⚠️ оплачено N ₽ вместо M ₽»: пересчёт выдачи — решение менеджера, не автомат.

**Уведомления:** менеджеру в рабочий чат (`send_telegram_notification`) — партнёр, суммы,
клиент, номер сделки. Партнёру — в его TG по `referrer.telegram_user_id`, как это делает
бот: «оплачен инвойс `AB-7`, N ฿». Для `referrer.is_test = true` не слать ничего.

## 7. Кабинет

Блок «Ссылки на оплату» в `static/referrer/index.html`, между реф-ссылками и выплатами,
виден только при `can_create_links`:

- Форма: сумма с переключателем ₽ / ฿ (по умолчанию ฿ — привычка агентов из бота),
  имя клиента и контакт опционально. Дебаунс 500 мс → `quote` → строка
  «Клиент платит **N ₽** → получает **M ฿**, курс X». Кнопка активна только
  при валидной котировке.
- Результат: номер (`AB-7`), ссылка, кнопка «Скопировать» (переиспользуем `copyUrl()`).
- Список ссылок: дата, номер, ₽ → ฿, клиент, статус-бейдж, копирование,
  «Отменить» у `pending`. Пагинация через `renderPager()`.

Стиль — существующие классы кабинета (`ref-url`, `pager`, модалки выплат).

## 8. Тесты

- `can_create_links=false` → 403 на всех четырёх эндпоинтах.
- `auth_mode='link'` + попытка включить флаг → 400.
- Чужая ссылка: чтение/отмена по токену другого партнёра → 404.
- Котировка: ввод в ₽ и в ฿ на одной сумме дают согласованную пару (round-trip).
- markup-партнёр получает курс хуже стандартного ровно на свою наценку; revshare — стандартный.
- Ответ `quote` не содержит `profit_usdt`, `commission`, `rub_usdt`, `usdt_thb`.
- Создание игнорирует клиентские `rate`/`amount_thb`.
- `webhook_url` из тела запроса к `/api/proxy/create-payment` не пробрасывается.
- Вебхук с неверным секретом → 401, сделки нет.
- Вебхук с верным секретом, но Доверка отвечает `PENDING` → сделки нет
  (тело запроса не является доказательством оплаты).
- `PAID` → ровно одна сделка; повторный вебхук и последующий поллер не дублируют.
- `amount_from ≠ amount_rub` → сделка есть, `payout_amount_thb` пуст, флаг в уведомлении.
- Строка в `deal_agents` с `comp_model` партнёра.
- Лимиты: 21-я ссылка за час → 429; 6-я висящая `pending` → 429.
- `is_test` партнёр → уведомления не уходят.

## 9. Порядок выкатки

1. Миграция колонки и таблицы, чекбокс в CRM. Флаг у всех выключен — прод не меняется.
2. Котировка, создание, блок в кабинете. Включаем одному агенту, проверяем ссылку.
3. Вебхук и поллер, проверка на реальной оплате мелкой суммой.
4. Заводим остальных агентов бота как `Referrer` с их процентом.

До пункта 3 оплата по ссылке нигде в CRM не отражается — включать агентам раньше нельзя.

## 10. Открытые вопросы

- `EXGREEN_PARTNER_SECRET_KEY` и `/api/calculate_partner` на VPS остаются у бота.
  Мы их не используем, но `.claude/docs/CLAUDE-api-server.md` про этот эндпоинт
  не знает вовсе — доку надо дописать отдельной задачей.
- Бот заводит сделки в Битрикс C18 (`corp.maksfin.ru`), который по нашим записям
  заморожен. Это не блокер для этой спеки, но означает, что учёт агентов бота
  сейчас уезжает в мёртвую воронку.
