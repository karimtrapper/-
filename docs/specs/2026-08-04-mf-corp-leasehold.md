# Бизнес-требования: сделки по недвижимости через MF Corporation (leasehold)

**Дата:** 2026-08-04
**Статус:** согласовано в части модели — блокирующие вопросы закрыты 04.08 (§9), можно планировать разработку
**Источник:** [таблица «Cделки недвижимость»](https://docs.google.com/spreadsheets/d/1OhcHOoAI3_EMplg-VaP3lI8FjhOahA3jY7f62T3pkg4/edit)
(листы `февраль`, `март`, `май leeshold`, `май freehold`, `июнь leasehold`, `июль leasehold`, `Balance (остаток)`)
**Затрагивает:** CalcCRM (модель, форма сделки, дашборд, выгрузка в Sheet)
**Объём первого этапа:** только leasehold. Freehold — отдельный этап (§8).

---

## 1. Зачем

Сегодня сделки по недвижимости живут в отдельной Google-таблице и заполняются руками.
В CalcCRM их либо нет, либо они заведены как «обычная сделка», и тогда цифры врут: у обычной
сделки одна прибыль и один карман, а здесь **деньги расходятся по двум карманам** —
часть остаётся в батах на счёте тайской компании (MF Corporation), часть в USDT в крипте.
Из-за этого дашборд, юнит-экономика и реферальные начисления считаются не по факту.

Задача — завести отдельный **тип сделки «Недвижимость через MF Corp»**, который повторяет
логику таблицы, считает всё сам и выгружается в тот же лист.

## 2. Как это работает сегодня (as-is)

### 2.1 Поток денег

```
Клиент ──USDT / RUB──► Grusha (кошелёк)
                          │
                          ├── покупаем баты по «курсу покупки»
                          │
                          ├──THB──► MF Corporation ──THB──► застройщик (сумма инвойса)
                          │            └── остаётся комиссия компании (≈1% в батах)
                          │
                          └── остаток USDT остаётся в крипте
                                   └── часть уходит агенту/рефералу
```

Клиент переводит **с запасом**: чтобы оплатить инвойс на ฿1 000 000, ему называют сумму
в USDT, посчитанную по «курсу продажи» (курс клиента). Мы покупаем баты дешевле —
по «курсу покупки». Разница курсов и есть наш заработок; часть его оседает в тайской
компании как её комиссия, остальное остаётся в крипте.

### 2.2 Проверенные формулы (сверено по строкам за май–июль)

| Величина | Формула | Пример (июль, «находкина bho property») |
|---|---|---|
| Курс продажи клиенту | `курс_покупки × (1 − спред%)` | 33.20 − 1.5% = **32.702** |
| Приход USDT (usdt-thb) | `сумма_THB / курс_продажи` | 16 742 400 / 32.702 = **511 968.69** |
| Приход USDT (rub-*) | `сумма_RUB / курс_брокера` | 1 578 090.20 / 79.185 = **19 929.17** |
| Себестоимость USDT | `отправлено_в_компанию / курс_покупки` | (16 742 400 + 0.9%) / 33.20 = **508 827.76** |
| — стоимость самого инвойса | `сумма_THB / курс_покупки` | 622 370 / 33.22 = **18 734.80** |
| Валовый доход | `приход − себестоимость` | 19 929.17 − 18 734.80 = **1 194.37** |
| Отправлено в MF Corp, THB | `сумма_THB + комиссия_компании_THB` | май: 2 238 435.71 + 28 858.69 = **2 267 294.40** |
| Комиссия компании, THB | `отправлено − сумма_THB` (или `% × сумма_THB`) | 1% × 622 370 = **฿6 223.70** |
| Комиссия компании, USDT | `комиссия_THB / курс_покупки` | 6 223.70 / 33.22 = **187.35** |
| Выплата партнёрам | три режима, каскадом по уровням (§3.5) | **$323.00** |
| **Остаток в крипте** | `доход − комиссия_компании_USDT − партнёры` | 1194.37 − 187.35 − 323.00 = **$684.02** |
| **Чистый доход** | `остаток в крипте + комиссия компании в USDT` | 684.02 + 187.35 = **$871.37** |

**Чистый доход — это сумма двух карманов: крипта + компания (в USDT).** Проверено на всех
строках июля: 684.02 + 187.35 = 871.37 · 97.85 + 47.01 = 144.87 · 1654.95 + 793.32 = 2448.26.
Именно это число показываем в карточке сделки и шлём в Telegram.

**Важно (уточнено 04.08 после разбора на живой форме):** баты покупаем ВМЕСТЕ с комиссией, поэтому
себестоимость считается от всей отправляемой суммы, а не от инвойса. Иначе «осталось в крипте»
завышается ровно на комиссию и кажется, что в компании можно оставить больше, чем есть.
Чистый доход от этого не меняется — тождество `приход − инвойс/курс`.

Ключевое: **«чистый доход» и «остаток в крипте» — разные числа.** Первое — сколько заработал
бизнес целиком, второе — сколько реально доступно в USDT прямо сейчас. Разница ровно на комиссию,
запертую в батах на счёте тайской компании.

### 2.3 Процент компании — кастомный, база = сумма инвойса в THB

Фактические значения за май: 1.00%, 1.03%, 0.94%, 0.80%, 0.76%, 0.74%; за июнь–июль — 1%.
**Процент задаётся руками для каждой сделки** (1% — привычная величина, не константа),
считается **от суммы инвойса в батах**. Система обязана допускать любой процент
и — что важнее — уметь считать его **обратно из фактически отправленной суммы**.

Занижают его не случайно, а осознанно — чтобы хватило на выплаты партнёрам из крипты (§3.6).

### 2.4 Что ещё есть в таблице

- **«от кого»** — партнёр, приведший сделку (Диана, Артур FazWAZ, insight, ex24, «99»).
  Это те же партнёры, что уже заведены в CalcCRM как рефереры.
- **«доход Катики в батах / в USDT»** — отдельная выплата номиналу тайской компании.
  Почти везде 0, один раз ฿20 000.
- **Документы**: `инвойс`, `договор`, `оплата` — сейчас текстовые пометки («есть», «инвойс»).
- **Хэш транзакции** — иногда несколько, иногда ссылка на TronScan.
- **Лист `Balance (остаток)`** — отдельный учёт по конкретной сделке с землёй:
  пополнения / списания / остаток, уходящий в минус («Овердрафт» в марте, −฿93 548).

## 3. Что заводим в системе

### 3.1 Тип сделки

К существующим добавляется **«Недвижимость через MF Corp»** (`deal_kind = 'mf_realty'`).
Обычные обменные сделки не меняются вообще — новый тип живёт рядом.

### 3.2 Поля сделки

**Вводит оператор:**

| Поле | Обяз. | Комментарий |
|---|---|---|
| Назначение | да | проект / юнит / номер инвойса — как в колонке «Назначение» |
| Дата | да | дата платежа |
| Направление | да | `usdt-thb` / `rub-thb` / `rub-usdt` |
| Партнёр («от кого») | нет | выбор из существующих рефереров |
| Сумма инвойса, THB | да | сколько должен получить застройщик |
| Курс продажи (клиенту) | для `usdt-thb` | по нему клиент считает свой перевод |
| Курс покупки (наш) | да | по нему мы покупаем баты — база себестоимости |
| Сумма RUB + курс брокера | для `rub-*` | вместо курса продажи |
| Приход USDT | да | по частям, несколько хэшей — механизм уже есть |
| Процент компании **или** отправлено в MF Corp, THB | да | одно вводим — второе считается (§3.3) |
| Выплата агенту | нет | существующий блок агентов |
| Выплата Катике (THB / USDT) | нет | редкая, но бывает |
| Документы: инвойс / договор / подтверждение оплаты | нет | статус + ссылка на файл |

**Считает система:**

- себестоимость USDT, валовый доход;
- комиссия компании в THB и в USDT;
- сумма к отправке в MF Corp;
- остаток в крипте;
- чистый доход;
- фактический процент компании.

### 3.3 Ввод «в две стороны»

Оператор работает то от плана, то от факта, поэтому нужны оба направления:

- **вперёд:** ввёл процент (1%) → система показала, сколько батов отправить в MF Corp;
- **назад:** отправил ฿2 267 294.40 по факту → система вывела процент (1.29%) и комиссию.

Второе поле всегда пересчитывается и остаётся видимым — как в возмещениях, где сумма
переводов и введённая вручную сумма показываются рядом.

### 3.4 Выплаты партнёрам — три режима

Партнёр может брать вознаграждение по-разному, и в одной сделке режимы **комбинируются
каскадом по уровням** (механизм уже есть в CalcCRM, добавляем один новый режим):

| Режим | База | Пример |
|---|---|---|
| Фиксированная сумма | — | «$300 за сделку» |
| **% от курса** (`markup`) | объём сделки в USDT | SID: 0.5% × 512 000 = **$2 560** |
| **% от прибыли в крипте** (новый, `crypto_share`) | `доход − комиссия компании − выплаты старших уровней` | Валера: 10% от того, что реально осталось в крипте |

Существующий `revshare` считает процент от валовой прибыли сделки. Для этих сделок нужна
база «то, что осталось в крипте» — иначе партнёру начисляется доля от денег, часть которых
заперта в батах.

### 3.5 Разобранный кейс: SID + Валера (сделка #458)

Реальная сделка, на которой видно, зачем нужен §3.6:

```
приход 512 000 USDT · инвойс 16 742 400 THB
├─ ур.1  SID (консьерж)   markup 0.5% от объёма      → $2 560   забирает сразу
├─ ур.2  Валера           10% от прибыли в крипте →  ~$…     из крипты
└─ на компанию отправлено 0.9% вместо 1%
```

Логика решения: **0.1% сознательно оставили в крипте**, потому что выплата Валере уходит
в USDT, а комиссия оседает в батах. Отправь мы полный 1% — на выплату не хватило бы, пришлось бы
либо конвертировать баты обратно, либо платить из своего кармана.

> ⚠️ Сейчас эта сделка в CRM показывает Валере **−$−256.00**: сделка ждёт возмещения, прибыль
> ещё не известна (0), каскад берёт базу `0 − 2560 = −2560` и выдаёт отрицательную выплату.
> Отдельный дефект, чинится вместе с этой задачей (см. R9).

### 3.5.1 Процент компании ↔ партнёр на крипте: связанные рычаги

Пока партнёров нет (или они на фиксе/проценте от курса), процент компании — просто
дележ одного и того же чистого дохода между карманами: снизил процент — больше осталось
в крипте, чистый доход тот же.

**С партнёром на модели «% от прибыли в крипте» это перестаёт работать.** Его база — то,
что осталось в крипте, поэтому чем меньше оставили компании, тем больше он забирает:

| Процент компании | В крипте | Валере (10%) | Наш чистый доход |
|---|---|---|---|
| 0.9% | $3 172.24 | $61.22 | **$5 089.62** |
| 0.5% | $5 189.40 | $262.94 | **$4 887.90** |

То есть занижение процента ради того, чтобы хватило крипты на выплату, само по себе
эту выплату и увеличивает. Оператор должен это видеть — сводка показывает выплату
партнёра сразу, поэтому эффект заметен при вводе, а не постфактум.

### 3.6 Подбор процента компании под выплаты

Прямое следствие кейса выше. Рядом с процентом компании система показывает баланс:

```
В крипте останется:      $X
Выплаты партнёрам:       $Y
──────────────────────────────
Свободно / дефицит:      $Z      ← красным, если меньше нуля
```

и кнопку **«подобрать процент»** — максимальный процент компании, при котором остатка в крипте
хватает на все выплаты партнёрам. Это ровно та арифметика, которую сейчас делают в уме
(«поставлю 0.9, потому что Валере ещё платить»), только без риска ошибиться.

Если оператор всё же ставит процент, при котором `Z < 0` — не блокируем, но предупреждаем:
«не хватит $N в крипте, придётся конвертировать баты».

### 3.7 Два кармана — обязательное разделение

Сделка порождает **две записи о доходе**, а не одну:

| Карман | Валюта | Где лежит | Доступен для выплат? |
|---|---|---|---|
| Комиссия MF Corp | THB | счёт тайской компании | нет — только через компанию |
| Остаток | USDT | наш кошелёк | да |

Без этого разделения дашборд покажет прибыль, которой физически нет в крипте.

## 4. Что система должна показывать

1. **В карточке сделки** — **чистый доход** (крипта + компания в USDT) как главное число,
   под ним расшифровка по карманам, фактический процент, сумма отправки в MF Corp,
   все хэши прихода, статусы документов.
1b. **В Telegram** — то же самое число в уведомлении по сделке: чистый доход и расшифровка
   «в крипте $X · в компании $Y». Сейчас в TG уходит только выплата агентам.
2. **Баланс тайской компании** — накопленная комиссия в батах: сколько пришло, сколько
   выплачено (Катике, на расходы), сколько осталось. Это прямой аналог листа `Balance`.
3. **В дашборде** — доход по недвижимости отдельной строкой, с разбивкой «в батах / в крипте».
   В общую прибыль обменника не подмешивать.
4. **Выгрузка в Google Sheet** — в тот же файл, лист по схеме `<месяц> leasehold`,
   колонки один в один с текущими, чтобы старые строки и новые лежали вместе.

## 7. Риски

| # | Риск | Чем грозит | Что делаем |
|---|---|---|---|
| R1 | **Смешение двух карманов** | прибыль на дашборде есть, денег в крипте нет | разделение на уровне модели, а не отображения (§3.4) |
| R2 | **Ошибка в курсе покупки** | искажает и себестоимость, и комиссию компании — при суммах до $650 000 за строку цена ошибки в сотнях долларов | подстановка курса из калькулятора + предупреждение при отклонении от рынка > 1% |
| R3 | **Захардкоженный 1%** | по факту 0.74–1.03%; сделки посчитаются неверно | процент всегда редактируемый + обратный расчёт из факта (§3.3) |
| R4 | **База выплаты агенту не определена** | партнёру начислят не ту сумму — прямые деньги | закрыть вопрос §9.2 до разработки |
| R5 | **Комиссия в батах — это выручка юрлица** | налоги/отчётность не учтены, риск расхождения с бухгалтерией MF Corp | на первом этапе только фиксируем; сверку с бухгалтерией — отдельно |
| R6 | **Ручной ввод больших сумм** | опечатка в разряде проходит незаметно | сверка прихода с суммой хэшей (уже есть), подтверждение при сумме > $100k |
| R7 | **Двойное заведение сделки** (в таблице и в CRM) | расхождение источников правды | после запуска таблица заполняется ТОЛЬКО выгрузкой из CRM, руками — не трогаем |
| R8 | **Исторические строки** | февраль–март заведены по другой схеме колонок | импортируем **только с мая** (решено), февраль–март остаются архивом в таблице |
| R9 | **Каскад считает от неизвестной прибыли** | пока сделка ждёт возмещения, `profit = 0`, и партнёр ур.2 получает отрицательную выплату (`−$−256` на #458) | до возмещения показывать «ожидает», а не число; выплату фиксировать после расчёта прибыли |
| R10 | **Комиссия занижается «на глазок»** | ошиблись в уме — либо конвертируем баты обратно, либо платим партнёру из кармана | подбор процента + индикатор дефицита (§3.6) |

## 8. Freehold — следующий этап

Другая механика, отдельный набор полей (лист `май freehold`):
оплата уходит в USD по SWIFT, появляются **комиссия за SWIFT (0.70%)** и **фиксированный
расход за платёж ($100)**, доход = `получено USDT − отправлено USDT − комиссии`.
Пример: получено 39 533.77, отправлено 39 373, доход 160.77.
Проектируем после запуска leasehold, на той же модели двух карманов.
