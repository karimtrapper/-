# Хэши приходов: один хэш на несколько сделок

**Статус:** реализовано 2026-08-14 (`c3b2bed`) — бэкенд, форма, карточка. Экран пула не делали
**Дата:** 2026-08-13

## Проблема

Клиент платит рублями несколько раз (Роман — три оплаты), а обмениваем мы
один раз и получаем **один** USDT-перевод на все три сделки. Сегодня в CRM
это выразить нечем:

- `Deal.payin_tx_hashes` — JSON `[{hash, amount_usdt}]` **на сделке**. Одна
  сделка → много хэшей есть, обратного (один хэш → много сделок) нет.
- Сумма в JSON — то, что вбил человек. Сверки с блокчейном нет: можно
  написать «$39 000» под хэшем, по которому пришло $3 900, и никто не заметит.
- Один и тот же хэш можно поставить в три сделки целиком — учёт покажет
  тройной приход.
- Для рублёвых методов (СБП, реквизиты) блок хэшей вообще скрыт, если сделка
  не про недвижимость: рубли пришли, а куда делись после конвертации — не
  видно.

Итог: «деньги пришли на Сбер, а конвертировали мы их или нет — непонятно,
лежат ли они на счёте, откуда пришли».

## Готовый образец в этом же коде

Ровно эта задача уже решена для **возмещений** (`ReimbursementTx` +
`ReimbursementTxUse`, коммит от 2026-05): перевод фаундеру — сущность с
суммой, возмещения берут из него доли, `used_usdt()` считает разобранное,
остаток виден, дважды один перевод не провести. Делаем зеркало для прихода.

## Модель

```
PayinTx                      # входящий USDT-перевод (один хэш)
  tx_hash      unique
  amount_usdt                # сколько реально пришло
  source       tronscan|manual
  tx_time, wallet_id, notes

PayinTxUse                   # сколько из перевода отнесено на сделку
  tx_id, deal_id, amount_usdt
  unique(tx_id, deal_id)
```

Инвариант: `Σ uses.amount_usdt ≤ PayinTx.amount_usdt` (допуск 0.01).
Превышение — ошибка сохранения с текстом «в хэше 3b56720f… осталось $544,
пытаетесь отнести $900», как `_sync_sber_claims` ругается на чужой приход.

## Синхронизация

`_sync_payin_tx_uses(session, deal, hashes)` — по образцу
`_sync_sber_claims`: сперва снимает use'ы, убранные из сделки, затем
добавляет новые с блокировкой строки (`with_for_update`) от гонки двух
менеджеров. Фронт продолжает слать `payin_tx_hashes: [{hash, amount_usdt}]`
— формат payload не меняется, учёт появляется на бэкенде.

## API

| Метод | Путь | Зачем |
|---|---|---|
| GET | `/api/payin-txs?unallocated=1&q=` | Пул хэшей: сумма, разобрано, остаток, в каких сделках |
| POST | `/api/payin-txs` | Завести хэш (тянем сумму из сети, `manual` — фоллбэк) |
| GET | `/api/payin-txs/<hash>` | Детали + разбивка по сделкам |
| DELETE | `/api/payin-txs/<id>` | Удалить хэш без аллокаций |

Сумма из сети — TronGrid/TronScan по хэшу (уже есть `_tron_usdt_transfers`,
`GET /api/tronscan/verify/<tx_hash>`).

## UI

- **Форма сделки**, блок хэшей: под каждым хэшем строка «в сети $39 544 ·
  разобрано $39 000 (сделки #479, #480) · **остаток $544**». Красным, если
  сумма долей больше сети.
- **Карточка сделки**: у хэша видно, что ещё в него входит — сейчас видно
  только свою часть.
- **Экран «Приходы USDT»** (вкладка рядом с возмещениями): хэши с
  нераспределённым остатком. Это и есть ответ на «обменяли или нет»: рубли
  забраны из пула Сбера, а обмена под них нет — хэша с их суммой не заведено.
- Блок хэшей перестаёт прятаться на СБП/реквизитах (сейчас `txHashGroup`
  скрыт для сберовских методов, если это не недвижимость).

## Миграция

Бэкфилл из существующих `payin_tx_hashes`: на каждый уникальный хэш —
`PayinTx` (сумма = сумма долей, `source='manual'`, пометка «сумма из CRM, не
сверена»), на каждую сделку — `PayinTxUse`. `Deal.payin_tx_hashes` остаётся
как есть (её читают выгрузки и Telegram), становясь проекцией аллокаций.

## Решения (2026-08-14)

1. **Сумма хэша** — тянем из сети (`_tron_tx_usdt_amount`, TronScan
   `transaction-info`, таймаут 6с без ретраев: сохранение сделки не должно
   висеть). Сеть молчит — ставим заявленную долю и `source='manual'`.
   **Важное уточнение, найденное при реализации:** потолок «сумма долей ≤
   пришедшего» строгий ТОЛЬКО при `source='tronscan'`. У `manual` сумма равна
   первой заявленной доле, то есть выдумана, и отказ по ней заблокировал бы
   вторую сделку навсегда из-за случайной недоступности TronScan. Такой перевод
   вместо отказа поднимает сумму до разобранного и остаётся помечен «не сверен».
2. **Экран пула** — НЕ делали. Есть `GET /api/payin-txs?unallocated=1` и
   `GET /api/payin-txs/<hash>`; остаток виден в форме под хэшем и в карточке
   сделки. Отдельная вкладка — следующий шаг, если понадобится сводный обзор.
3. **Рублёвая сторона** — хэш на сделку, как и было. Цепочка «рубли → сделка →
   хэш» собирается через `payin_parts`, третья сущность не понадобилась.

## Что сделано

* `PayinTx` + `PayinTxUse`, миграция через `create_all` по этим двум таблицам.
* `_sync_payin_tx_uses(session, deal, parts)` по образцу `_sync_sber_claims`,

* `get_used_transaction_hashes`: приходный хэш занят только при нулевом остатке;
