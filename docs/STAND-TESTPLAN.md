# Тест-план задачника — проверка флоу перед продом

Документ для QA-агента (`qa-tester`) и для человека. Цель — пройти все пути сделки
ролями, сверить цифры и найти то, что сломает работу людей, до того как задачник
поедет из ветки `stage` в `main`.

Правило одно: **факт получаем запуском, а не чтением кода**. Каждый пункт ниже —
действие в браузере и наблюдаемое ожидание. Непроверенное помечается `open`, а не
«наверное работает».

---

## 0. Как поднять стенд для прогона

Живую доску (`https://stand-app-production.up.railway.app`) прогонами **не трогаем**:
по ней ходят люди, а «Сбросить всё» чистит её у всех. Прогон — на локальной копии.

**Один прогон — свой порт, своя база, своя сессия браузера.** Два агента на одном порту
мешают друг другу: чужие входы съедают лимит, роль в браузере подменяется, а `kill` по
порту молча гасит чужой сервер (пойман на пробном прогоне 24.09). Поэтому порт берём
свободный и чужие процессы не убиваем:

```bash
cd Dev/CalcCRM-stage
RUN=qa$(date +%H%M%S)                      # метка прогона
PORT=$(python3 -c "import socket;s=socket.socket();s.bind(('',0));print(s.getsockname()[1])")
STAND_MODE=1 DATABASE_URL=sqlite:////tmp/stand_$RUN.db STAND_PASSWORD=loc \
  PORT=$PORT SECRET_KEY=loc nohup python3 app.py > /tmp/stand_$RUN.log 2>&1 &
echo "$!" > /tmp/stand_$RUN.pid; echo "RUN=$RUN PORT=$PORT"
export AGENT_BROWSER_SESSION=$RUN          # в каждом вызове Bash — переменные не живут между вызовами
```

**Лимит входов: 5 в минуту** на всё приложение, шестой отдаёт 429 (в браузере выглядит
как «зависло на /login»). Входы через curl тоже в счёт. Между сменами ролей — пауза, или
держать cookie jar на каждую роль (`/tmp/$RUN-<логин>.jar`) и входить один раз: при том
же `SECRET_KEY=loc` cookie переживает и перезапуск сервера.

`STAND_TG_TOKEN` не задаём — локальная копия в Telegram не пишет.
Логины те же, пароль `loc`: `karim` (админ), `marina` (менеджер), `artem`
(операционист), `vitaliy` (фин дир), `teodor` (Теодор).

**Доска.** Два варианта:

- Чистая демо-доска: **засевается сама** при первом входе `karim` в задачник (13 сделок,
  тост «Добавлены примеры»). «Добавить примеры» на непустой доске засевает второй
  комплект (26 сделок) — жать её только после «Сбросить всё». «Сбросить всё» открывает
  `confirm`: сначала клик, потом отдельной командой `dialog accept`, не параллельно.
- Копия живой доски (чтобы проверять ровно то, что увидят люди) — только чтение с прода:

```bash
B=https://stand-app-production.up.railway.app; L=http://127.0.0.1:$PORT
curl -s -c /tmp/live.jar -X POST $B/api/auth/login -H 'Content-Type: application/json' \
  -d '{"username":"karim","password":"<STAND_PASSWORD из Railway>"}' >/dev/null
curl -s -b /tmp/live.jar $B/api/stand/state > /tmp/live_state.json
curl -s -c /tmp/loc.jar -X POST $L/api/auth/login -H 'Content-Type: application/json' \
  -d '{"username":"karim","password":"loc"}' >/dev/null
python3 -c "import json;d=json.load(open('/tmp/live_state.json'));json.dump({'data':d['data'],'version':0},open('/tmp/put.json','w'))"
curl -s -b /tmp/loc.jar -X PUT $L/api/stand/state -H 'Content-Type: application/json' -d @/tmp/put.json
```

В конце: `npx agent-browser close`, `kill $(cat /tmp/stand_$RUN.pid)` — только свой сервер.

## 1. Как ходить по экранам (грабли автоматизации)

- Браузер — `npx agent-browser` в сессии `$RUN` (см. раздел 0).
- **Вход по паролю.** Форма `#pwForm` скрыта, а «Вход по паролю» — переключатель: второй
  клик её прячет. Ссылки `@eN` из snapshot после этого протухают. Надёжно так:
  `open $L/login` → `wait 1500` → `click '#pwToggle'` → `fill '#loginUsername' <логин>` →
  `fill '#loginPassword' loc` → `click '#loginBtn'` → проверить, что адрес стал `/crm`.
- **Выход:** `eval "fetch('/api/auth/logout',{method:'POST'})"` — только с открытой
  страницей стенда; в пустой вкладке (about:blank) падает «Failed to parse URL».
- **После входа убедиться, что `S.role === standMe`** (`eval "S.role+' / '+standMe"`). Браузер
  автоматизации иногда восстанавливает из кэша страницу прошлого пользователя — тогда
  свой шаг показывается как чужой («Сейчас ход роли …»). Лечится повторным `open` задачника.
  У живого человека такого нет: роль ставится с сервера до первой отрисовки.
- Переключатель ролей только у `karim`, кнопки подписаны со счётчиком («Менеджер 2») —
  искать по началу текста. Остальные видят одну неактивную плашку своей роли.
- **Прямой переход** `/tasks?deal=<id>` открывает «Карточку сделки» (не задачу) и сразу
  стирает параметр из адреса. Шаг — вкладка «Текущая задача».
- Кнопки искать `find text "…" click`; селектор `button:has-text(...)` agent-browser не понимает.
- **Поля с `onchange`, а не `oninput`**: после `fill` нажать `Tab`, иначе значение не
  попадёт в состояние. Проверять себя через `eval "JSON.stringify(S.deals.find(d=>d.id===1479))"`.
- Стабильные id полей на шаге «Что делаем с USDT»: `#pc_<id>` назначение,
  `#cr_<id>` курс Coins, `#ct_<id>` баты, `#cad_<id>` адрес, `#ca_<id>` сумма USDT,
  `#cw_<id>` кошелёк возврата фаундеру. На шаге «Отправить с кошелька»: `#sh_<id>`
  ссылка на транзакцию, `#sa_<id>` сумма, кнопка `button[onclick='sendAdd(<id>)']`.
- Селекторы по порядку (`combobox` №3) ненадёжны: после выбора назначения в карточке
  появляются новые селекты (сеть, кошелёк), и порядок сдвигается.
- Диалоги: «Вернуть с вопросом» открывает `prompt`, «Сбросить всё» — `confirm`. Сначала клик, потом отдельной командой `agent-browser dialog accept "<текст>"`; пока диалог открыт, `eval` и `snapshot` не работают.
- Тосты читать так: `eval "Array.from(document.querySelectorAll('[class*=toast]')).map(e=>e.innerText).join(' | ')"`.
- Уведомления: `eval "JSON.stringify(S.notes.slice(-6).map(n=>[n.role,n.text]))"` —
  кому и что ушло.
- Скриншот в полный рост рисует шапку посреди страницы — это артефакт снимка, не баг.

## 2. Эталонные формулы — по ним сверяем цифры на экране

| Что | Формула | Где в коде |
|-----|---------|------------|
| Удержание при отправке брокеру | валютный контроль 0,1 % + 40 ₽ (уходит наружу) + 0,2 % (остаётся на рублёвом счёте) — от всей суммы пачки | `BROKER_FEE`, `brokerSend` |
| Доля сделки в пачке | удержание делится по доле рублей сделки; доля USDT = (рубли сделки − её часть удержания) / курс брокера | `convMargin` |
| Ожидаем USDT | (рубли − удержание) / курс брокера | шаг s18 |
| Должны выдать | сумма батов всех сделок пачки; для мелких без батов — рубли / средний курс дня | `convMargin`, `approx` |
| Порог безубыточности | отправлено брокеру / (баты / курс USDT→THB) | `convMargin` |
| USDT для Coins | баты / курс Coins | `transferSet` |
| СБП-приход | в сделку идёт брутто: зачислено + комиссия эквайринга 0,96 % | ручной разбор прихода |
| Допуск прихода | по умолчанию 1 000 ₽, правится на шаге «Ждём приход» | `expect.tol` |
| Курс уехал | расхождение курса сделки с курсом дня больше 0,5 % → предупреждение и «Запросить курсы заново» | `RATE_DRIFT` |
| Стартовые балансы | IPPS 1 250 000 ฿ · касса 480 000 ฿ · SCB 2 100 000 ฿ · USDT 41 800 | `balInit` |

Контрольный пример (демо-засев после правок 24.09): очередь — 5 обменов на 754 000 ₽
(Полякова 238 000, Мартиросян 64 000, Ким 156 000, Гурьев 84 000, Соколова 212 000).
Пачка СД-1479 (931 000 ₽, 350 000 ฿, клиенту 2,66) + 5 мелких = 1 685 000 ₽ → удержано
5 095,00 ₽ (1 725,00 + 3 370,00) → брокеру 1 679 905,00 ₽ → по 81,40 = $20 637,65; должны
выдать 639 999 ฿ = $20 512,79 по 31,2 → плюс $124,87 (0,61 %), порог 81,9. Доли: СД-1480
$1 028,82 · СД-1476 $2 596,55. Coins 350 000 ฿ по 31,20 = 11 217,95 USDT; 81 538 ฿ по
31,00 = 2 630,26 USDT (Соколова в минусе на $33,71 — должно быть предупреждение).

## 4. Правила по этапам — чек-лист

Последние решения Карима на 24.09. Отменённое в скобках, чтобы не принять старое
поведение за баг и наоборот.

**Заявка и клиент**
- Заявка — один экран (не мастер «Шаг 1 из 2»). Источник обязателен: Telegram / WhatsApp / Битрикс / «Без переписки»; живой поиск по подстроке («мар» → Мартиросян и Соколова Мария), счётчик «Найдено N из M», фокус не теряется, смена канала сбрасывает поиск.
- После выбора чат сворачивается в строку «ОТКУДА КЛИЕНТ · …» с «Сменить источник» и «Оставить как было». «Чата нет в списке — вписать вручную» + «Привязать» → пометка «введён руками», клиентом становится ник (решено 24.09).
- Клиент только из справочника, имя руками не вводится. Нет карточки → имя из чата + «Создать карточку»; при сохранении создаётся клиент и `clientId`.
- Смена канала сбрасывает только автоматически узнанного клиента; выбранного руками не трогает. «Взять из карточки» подставляет и чат, и канал (номер WhatsApp не уходит в Telegram).
- Новый / старый клиент — автоматически по наличию договора (плашек «впервые» нет, история в карточке клиента).
- Тип: «Оплата недвижимости» (Лизхолд / Фрихолд / Аренда обязательно) или «Обмен валюты» (пары RUB→THB, USDT→THB, RUB→USDT, THB→USDT; USDT→THB оставляет только «Крипта», RUB→USDT — только рублёвые способы). «Перевод за товар» убран.
- Сумма обязательна. Вторая сумма — прикидка «≈» по курсу дня, не сохраняется.
- Кнопки «Создать заявку — курс спросит операционист» (сразу «Ответить курс», уведомление операционисту) и «Курс знаю — сам».
- Агенты: один блок «Агенты сделки», уровни, модели revshare / markup / fixed / % от прибыли в крипте, пресеты «Каскадом» и «В долю». Автоподстановка только при следе (метка Битрикса, закреплённый партнёр, прошлая сделка из чата с агентом). Нет следа — спокойная строка без плашек. Revshare не уходит ниже 0. У проваленной сделки начисление 0, но она входит в конверсию реферера. Пример Карима: 1 000 000 ₽ → брокеру 996 960 ₽ = 12 247,67 USDT, выдача 11 880,24, прибыль 367,43 (3 %), revshare 30 % = 110,23 $, markup 1 % = 122,48 $.

**Курсы**
- Контрагенты: RUB→USDT — Крипта-Платежи (Екатерина), Asia Capital, Tradex; USDT→THB — Coins.co.th, Bitazza (запасной). PRO100TRADE убран отовсюду. Брокер по умолчанию Tradex.
- Список редактируемый: «+ Добавить контрагента», «убрать» с подтверждением, «чат» для правки привязки. Личный аккаунт — «перейти с вопросом», группа — «перейти», вопрос в буфере.
- Вопрос брокеру «Какой курс на 2 850 000 ₽?», Coins «Which rate? usdt-thb, 1 000 000 THB» — без приписки «сумма примерная».
- У каждого контрагента строка и «Отправить» (не «Записать» и не общее «Отдать курсы менеджеру»). Отправленное сворачивается, есть «Редактировать» / «Сохранить» / «убрать». Журнал «Курс получен — …», «Курс обновлён — …».
- Лучший: RUB→USDT меньший, USDT→THB больший. Блок «Курсы контрагентов» у операциониста виден до прихода денег, после прихода пропадает.
- Уведомления менеджеру: «Новый курс · X — теперь он лучший в сделке», «Курс обновлён · …»; «прежний лучший» — снимок до правки. Операционисту: «запросил заново» (с причиной, ответы очищены) и «взял не лучший».

**Расчёт клиенту**
- Курс и сумма клиенту связаны в обе стороны: 2,85 × 5 000 000 ฿ = 14 250 000 ₽; 14 000 000 ₽ → курс 2,8. Брокер 81,10 → 79,50: себестоимость 2,5994 → 2,5481, наценка +9,64 % → +11,85 %, сумма клиенту не меняется. Вставка «2.568221 ₽/฿» чистится до числа.
- Кнопки «Клиент согласен», «Запросить курсы заново», «Клиент отказался». «Открыть в калькуляторе» передаёт курсы, сумму, тип и метод «Кастом» параметрами адреса.

**Документы и договор**
- Новый клиент: паспорт и инвойс обязательно, SPA и анкета ИПДС — если есть. Старый: только новый инвойс, строка паспорта видна.
- «Загрузить» явной кнопкой; клик по строке ничего не снимает. После загрузки имя · размер · время, «Открыть», «Убрать».
- Расхождение имён паспорт / SPA — жёлтое предупреждение, не блок. Машиночитаемая строка паспорта отображается.
- Договор: блоки по источнику (паспорт, инвойс, «ГЛАВНОЕ · СУММА И КУРС», «курс зафиксирован» со временем). Обязательны ФИО, паспорт, объект, сумма, курс; «700 000» сохраняется без NaN. PDF / DOC / «Загрузить свой» (версия +1) / «Вернуть сгенерированный».
- Отправка клиенту: реквизиты MF Corp с копированием по строке и «Скопировать всё»; подписанные документы необязательны, несколько файлов, снимаются при смене условий. На этом шаге нет полей курса и пересборки — только «Запросить курсы заново». Проверка курса дня: ≤ 0,5 % «Курс держится», больше — «Курс уехал на …» с направлением.

**Приход и реквизиты**
- «Ждём приход»: сумма, счёт, допуск, назначение редактируются; правка назначения помечается «Изменено вручную» с «вернуть как в договоре»; каждая правка — в журнал «было → стало».
- Ручной разбор, СБП 0,96 %, s14m с обязательной причиной — см. S9. Молча с недобором дальше не едет.
- «Реквизиты для оплаты» у менеджера сразу после прихода: получатель, банк, счёт, сумма, инвойс, срок, назначение для банка получателя («Payment for unit B1204, invoice INV-4072, Gusev Igor»). Без банка, счёта и назначения шаг не проходит.

**Конвертация, назначения, подписи**
- «Отправка брокеру»: шапка — объём всей пачки; обязательны брокер, курс, кошелёк; проверка маржи «Работаем в плюс / Уходим в минус» с порогом безубыточности по всей пачке, запись «Проверка перед отправкой: …».
- Удержание 0,3 % + 40 ₽ на пачку; 0,2 % в прибыль не входят (строка «Не в счёт сделки»). Проверки: 474 292,27 → удержано 1 462,88 → отправлено 472 829,39; 141 405,13 → 464,22 → 140 940,91.
- «Ждём USDT»: сумма не предзаполнена; перевод из входящих, несколько суммируются; ручной хеш сперва ищется по подстроке во входящих; иначе «сумма по заявке» / «сумма со слов»; повторный хеш не добавляется. Прибыль от факта, при пачке факт делится по доле рублей.
- Взятые мелкие исчезают из очереди и в другую пачку не попадают; курс пачки пишется во все её сделки. Крипто-сделки в рублёвую очередь не попадают вовсе.
- **Задачи заполняют карточку CRM (Карим, 24.09).** Каждый шаг пишет те же поля, что заполнили бы руками в CRM: Pay-In → конвертация (USDT, хеши) → Pay-Out (источник, баты, USDT, хеши выдачи). Возмещение — только когда баты выдал фаундер своими; выдача деньгами, которые пришли к нам, — просто расход в Pay-Out.
- **Pay-Out по назначению.** Coins → источник «Coins / Bitazza», баты, курс, после сети — USDT и хеш выдачи (у недвижимости ещё строка в «Переводы в MF Corp (факт)»). Клиенту на кошелёк → «USDT клиенту на кошелёк», USDT и хеш. IPPS → «Баланс IPPS», баты, баланс IPPS уменьшается. «Оставить на кошельке» → обязателен выбор «Откуда выдали баты» (касса / SCB), баланс уменьшается. Вернуть фаундеру → «Кошелёк фаундера», фаундер, «выдал свои баты», USDT к возврату; возмещение #R-<id> закрывается хешем после сети, либо сразу «автовозмещение», если USDT от брокера пришли на кошелёк этого же фаундера. Оплата инвойса с SCB дописывается строкой «Оплата инвойса», Pay-Out не затирает.
- **Закрытие мелких сделок пачки — как в CRM: когда клиент получил деньги.** При получении USDT стоят «В пачке — ждёт выдачи». IPPS, касса/SCB и возврат фаундеру (баты уже выдал фаундер) — закрываются сразу после решения по USDT; долг фаундеру живёт во вкладке «Возмещения». Coins и перевод клиенту — после ухода перевода в сеть.
- Вкладка «Возмещения»: «Не возмещено» (сделка, фаундер, баты, сколько вернуть, «ждёт перевода») и «Возмещено» (как закрыто, хеш).
- Сумма к отправке больше доли сделки — жёлтое предупреждение в карточке назначения: для Coins «будем в минусе», для остальных «лишнее уйдёт из денег других сделок пачки».
- «Известить Coins» — таблица по всем сделкам пачки с назначением Coins: баты, курс, сколько USDT реально ушло, хеши.
- Во входящих на «Ждём USDT» только переводы после отправки рублей; стенд сам кладёт два перевода брокера (60 % и остаток) через 1 и 2 минуты после отправки.
- Назначения по каждой сделке: Coins (курс + баты → USDT: 640 000 / 31,20 = 20 512,82), IPPS (задачи владельцу кошелька нет, «Возврат USDT» по умолчанию «не нужен»), «Оставить на кошельке», «Вернуть фаундеру» (кошелёк из списка), «Клиенту на кошелёк» (сумма и адрес). Сеть TRC-20 / ERC-20 обязательна и попадает в текст задачи. Сводка «пришло · уйдёт · останется». Без назначения шаг не проходит и называет сделку.
- Подписи: мультисиг — Виталий «Подписать N переводов — дальше их одобрит Теодор», затем Теодор «Одобрить вторым ключом»; личный кошелёк — владелец сам с хешем. Отправка частями, «Отправлено $X из $Y», «Закрыто: N из M»; «Подписал всё» блокируется с указанием сделки без ссылки. Путь не укорачивается задним числом: на оплате «14 из 15», на закрытии «15 из 15».
- Coins платит только на счёт MF Corp; оплата инвойса со счёта SCB без выбора источника, чек обязателен (несколько файлов); закрытие — «Чек клиенту и закрытие», кнопка неактивна до отметки «Чек отправлен клиенту».

## 7. Формат отчёта QA-агента

**Как запускать.** Агентом `general-purpose` с ролью QA и прямым указанием «выполняй сам,
других агентов не запускай». `qa-tester` на пробном прогоне 24.09 передал задачу
вложенному агенту и вернулся без результата, а вложенный параллельно пошёл на тот же
порт. Один сценарий или группа — один агент, у каждого свой `RUN` (раздел 0).

Одна таблица на сценарий: `шаг · роль · действие · ожидание · факт · PASS/FAIL/open`.
В конце: список FAIL с номером сценария, скриншотом (`/tmp/qa_<S#>_<шаг>.png`) и
предложением, что чинить; отдельно — какие B-баги из списка выше подтвердились или ушли.
Вердикт прогона — через `.claude/skills/falsify/scripts/falsify.py`: сценарий = ожидание,
непройденное = `open`. Прод (`main`) не трогать, живую доску не сбрасывать.
