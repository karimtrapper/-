## Реализация

1. SQL-реестр (`app.py`, `Wallet`, `_stand_seed_wallets`, `_wallet_registry_fields`): назначение, лимит, роли начала/подтверждения, одиночная подпись владельца, публичные адреса подписантов. Политика включается только у двух новых записей реестра. Обычный API редактирования кошельков не позволяет подменить политику или удалить служебный кошелёк. Старые записи сохраняются активными, с разовой пометкой `not_for_new_deals`; кошельки, созданные позже администратором, не получают эту пометку при рестарте.
2. Приход (`app.py`, `stand_transfers.py`, `static/stand/tasks.html`): ожидаемый кошелёк по назначению, проверка фактического получателя, постоянное предупреждение для новых кошельков с политикой, подтверждение расхождения реальным пользователем. Само подтверждение не зачисляет деньги: требуется выбрать фактический зарегистрированный кошелёк и повторить проверку. Неоднозначный или незарегистрированный получатель не угадывается. При нескольких выходах транзакции учитывается только сумма ожидаемого получателя. Отправитель помечается знакомым по реестру/подтверждённой истории либо новым.
3. s22: строка правил из реестра; назначение шага сохранено.
4. s23: серверный claim с аутентифицированным `AdminUser.id`, блокировкой записи и условным `UPDATE ... WHERE id AND version`. Задачу до claim видят разрешённые инициаторы. Победитель фиксируется один; проигравший получает 409 с именем. Кошелёк, сумма и поручение привязаны к отпечатку операции.
5. s24: отдельный серверный endpoint подтверждения. Инициатор не может подтвердить свою операцию даже после смены роли. Для одиночной отправки владельца маркер разрешения ставится при claim; завершение и пропуск s24 происходят только после проверенного Success. Поллер не заменяет подтверждение второго сотрудника. Общий PUT состояния не позволяет подделывать подписи, согласования и подтверждения расхождений.
6. CRM (`app.py`, `static/crm/crm.html`): кошельки поступления/выплаты, правила рядом с выбором, строгий boolean согласования, серверная проверка роли одобряющего. Лимит проверяется по большей из объявленной суммы выплаты и суммы распределённых исходящих переводов. Изменение суммы/кошелька/поручения лишает прежнее согласование силы. Проверены пути создания, редактирования, Доверки и закрытия задачника в CRM. При закрытии одобренной отправки сервер переносит исходного одобрившего с доски; клиент не может прислать поддельный маркер.

## Решения и ограничения

- Владелец соответствует существующей роли `teodor`, финансист — `findir`, операционист — `operator`.
- Порог $10 000 сравнивается с суммой USDT в соотношении 1:1. Это явное допущение для данного регламента, а не получение рыночного курса.
- Финансист может поставить отметку «согласовано владельцем»: отметка означает подтверждение полученного согласования владельца и сохраняет личность поставившего её сотрудника.
- Совместимость старых кошельков приоритетна: их прежние шаги, подписи и отказ 422 при неверном получателе сохраняются. Новая процедура постоянного предупреждения применяется к ожидаемым адресам двух новых кошельков. Новые сделки не выбирают кошельки с `not_for_new_deals`, существующие продолжают работу.
- До появления новых строк политики в реестре CRM сохраняет прежний путь без привязанного кошелька; стенд создаёт новые строки сидом. Для отдельного SQL-развёртывания подготовлен `scripts/wallet_registry_cutover.sql`; он здесь не выполнялся на внешней БД.
- Сверка криптографических подписантов из ответа TronScan не реализована: это разрешённое заданием сокращение объёма интеграции. Публичные адреса ролей показаны для сверки; подтверждение сети использует существующую проверку хеша. Адреса Mfstr не используются как адреса подписантов.
- UI-сценарий s24 использует явно документированную фикстуру локальной БД с pending-переводом без Success после настоящего claim. Она проверяет экран и права подтверждения, но не доказывает сетевое завершение. Success и пропуск s24 у владельца проверяются отдельными pytest-тестами.

- В ходе дизайн-приёмки устранено лишнее сохранение неизменившегося справочника рефереров при просмотре: `refsSync` сравнивает записи по значениям, сохраняет реальные изменения, сохраняет отклик ручной синхронизации. Серверная логика версий и финансовых проверок не ослаблялась.
- Совместимость СД-1483/1484/1487/1489 проверяется локальными фикстурами и общей регрессией; реальные сделки на живом стенде не открывались для изменения и не прогонялись как тестовые.
