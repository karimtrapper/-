## Вывод и риск для живого стенда

Воспроизведены два дефекта клиентской синхронизации действующего stage:

1. **Исчезновение новой сделки из памяти интерфейса (`S.deals=[]`).** Поздний
   ответ GET, начатого до создания сделки, применяется после успешного PUT и
   возвращает интерфейс, `standVer` и `standBase` к старому состоянию.
   **В этом воспроизведении в БД сделка осталась.** Следующий успешный поллинг
   может вернуть её; ввод в поле/пауза поллинга может задержать восстановление UI.
2. **Потеря локальной правки курса при 409.** Клиент выбирает серверную сделку
   целиком, если обе сессии изменили хоть что-то в одном объекте сделки.
   Независимая запись менеджера в журнал выбрасывает новый курс Coins и переход
   операциониста s5→s6. Повторный PUT заканчивается 200, но курса в нём уже нет.
   Показывается общий тост о конфликте; поле и действие не сохраняются.

**Да, на текущем stage есть риск потери введённых изменений и исчезновения сделки
из UI. Постоянное удаление уже сохранённой заполненной сделки из БД этими двумя
сценариями не подтверждено.** Нельзя объявлять конкретные прошлые эпизоды QA или
СД-1477 от 06.10 полностью объяснёнными без их сетевых трасс/снимков базы.
Воспроизведён механизм, соответствующий описанным симптомам; это не аудит
исторических данных и не доказательство отсутствия других причин.

## Как устроено сохранение

- `standSave()` отправляет общий снимок доски, не patch одного поля.
- Сервер `PUT /api/stand/state` не выполняет трёхстороннее слияние. Он берёт
  блокировку строки (`FOR UPDATE` на PostgreSQL, `BEGIN IMMEDIATE` на SQLite),
  сравнивает присланную версию и при конфликте возвращает 409 с актуальным снимком.
- Сервер проверяет переходы ролей, восстанавливает защищённые поля и запрещает
  исчезновение существующих заполненных сделок (`missing_deals_forbidden`).
  Отдельное существующее исключение — действительно пустой `manualNew` черновик.
- При 409 клиент вызывает `standMerge(base,mine,theirs)` и через 120 мс отправляет
  объединённый снимок повторно. До исправления массив `deals` сливался по ID,
  но изменённая с обеих сторон сделка была неделимой: выигрывал весь серверный объект.
- `standPull()` до исправления проверял только занятость сохранением в момент
  получения ответа, равенство версии, фокус ввода и недавний клик. Более старую
  версию он не отвергал, если PUT к этому моменту уже завершился.

Дополнительное ограничение исходного API: проверка версии пропускается при
`version: null`/отсутствии версии. Обычный исследованный клиент после загрузки
передаёт число; обход не использовался для воспроизведения. Обязательная версия
для всех записей — отдельное рекомендуемое усиление контракта API, требующее
проверки старых клиентов/скриптов. В этой ветке серверный контракт не менялся.

## Воспроизведение до исправления

`tests/test_stand_board_concurrency.py` поднимает настоящий локальный HTTP-сервер
Flask в изолированной БД. Создаёт два тестовых аккаунта с ролями manager/operator
(сценарии marina/artem), отдельные подписанные cookie-сессии. Node запускает два
изолированных JS-контекста и исполняет настоящие функции `standPull`, `standSave`,
`standMerge`, `standApply`, `standWaitSaved` из tasks.html. Подменены только задержки
доставки ответов; сервер, авторизация, проверки и запись в БД настоящие.
HTTP-прогон использует SQLite; PostgreSQL в этом исследовании не запускался.
Дефекты находятся в общем клиентском коде и не зависят от диалекта БД.
Это тест двух сессий синхронизации, не полный браузерный DOM-прогон.

Барьер удерживает уже полученный ответ GET до окончания PUT. Это устойчивее
случайного sleep: нужный порядок воспроизводится на каждом запуске. Скрипт печатает
время от начала, роль, HTTP-статус, версию, ID сделок; пароли не используются.

## Исправление

Изменён только клиент `static/stand/tasks.html`:

- GET запоминает версию при старте; если за время запроса локальная версия
  изменилась либо ответ содержит более старую версию, снимок не применяется.
  Это распространяется и на принудительное обновление.
- Для существующей сделки объединяются разные изменённые поля. Журнал
  объединяется только при дописывании к неизменённому общему префиксу.
- `quotes`, `rates`, `transfer` и прочие вложенные объекты/массивы остаются
  неделимыми: составная сумма/адрес или денежные поля не склеиваются по частям.
- При реальном конфликте любого поля остаётся вся серверная сделка и прежний
  явный тост; локальный переход шага отдельно не применяется.
- Получившийся снимок по-прежнему проходит все проверки API при повторном PUT.
  Никакие серверные права или финансовые проверки не ослаблены.
