## Подготовка, учёт результата и откат

1. Открыть `https://grusha-new.up.railway.app/login` → «Вход по паролю» → логин и пароль → `/crm` → `/tasks`. Пароль пяти штатных ролей берётся у владельца переменной Railway `STAND_PASSWORD`; в отчёт, снимки и этот файл его не писать. Войти по одному разу в разных профилях браузера: `karim` — admin, `marina` — manager, `artem` — operator, `vitaliy` — findir, `teodor` — teodor. Лимит — пять логинов в минуту. Админ может смотреть роль, но проверку доступа проводить **отдельной сессией нужного пользователя**. Прямой `/tasks?deal=N` открывает карточку, рабочий шаг — вкладка «Текущая задача». Если автоматизировать: после заполнения поля с `onchange` нажать Tab; при кэшированной странице роли открыть `/tasks` заново. [Грабли автоматизации](STAND-TESTPLAN.md#1-как-ходить-по-экранам-грабли-автоматизации).
2. До первого изменения сохранить в протоколе ID дампа T4, время среза и эталонные агрегаты **из restore этого же дампа**: число `deals` по статусу/виду, суммы `payin_amount_usdt`, `payout_amount_usdt`, `profit_usdt`, `net_profit_usdt`, `referrer_payout_usdt`, число `referrers`, `payout_requests`. Записать также исходные значения `/api/analytics/dashboard?period=all` и идентификаторы тестовых сделок. Не придумывать фиксированные числа: в плане дано 484 сделки до ночного среза, а окончательный дамп может отличаться.
3. Для всех новых записей использовать уникальный префикс `ТЕСТ T8-<ID>-<дата>` в имени клиента, объекте/комментарии и имени реферера. Файлы — обезличенные тестовые PDF/PNG с тем же префиксом; платёжные реквизиты и адреса кошельков — тестовые, согласованные для стенда. **Не выбирать реальных клиентов из копии прода, не менять их сделки, KYC, начисления или заявки.** Редактирование и удаление проверять только на своей специально созданной тестовой записи.
4. Разрешённые чтения сети не создают деньги: для Сбер-зеркала нужен **отдельно помеченный тестовый приход** в прод-пуле, предоставленный владельцем стенда. Если такого нет, записать `BLOCKED` для проверки зеркала и провести отдельный демо-кейс. Для реального хеша нужен тестовый подтверждённый перевод после создания сделки, на адрес тестового кошелька стенда; нельзя повторно использовать чужой/исторический хеш. Если сеть отвечает 429/недоступна, записать `BLOCKED: chain read` и повторить позже, не ставить PASS. Физическую оплату инвойса или отправку USDT ради UI не делать; учебные исходящие подтверждать только разрешённым демо-путём.
5. После **каждого** денежного кейса выполнить процедуру `Q` из блока «Тишина», сохранить снимок ответа и счётчиков. Приоритет P0 означает блокировку приёмки при FAIL или OPEN. В «Фактическое» вписывать URL, ID сделки/пачки/прихода/заявки, суммы, время, ответ API и ссылку на снимок; в PASS/FAIL ставить только `PASS`, `FAIL` или `BLOCKED` с причиной. Пустые колонки ниже предназначены для исполнителя.
6. Откат: в `/tasks` админом удалить только свои `ТЕСТ T8` задачи/тестовые поступления, если UI это позволяет и они не связаны с закрытыми сделками; в `/crm` удалить только созданные данным прогоном тестовые сделки, заявки и рефереров **после** записи ID и снимков. Сверить, что исторические строки остались по дампу. Если удаление каскадно меняет баланс/начисление, вместо удаления пометить тестовую запись и передать её ID владельцу для отката из проверенного бэкапа стенда; **«Сбросить всё» на общей доске не нажимать**. Проверка удаления CRM — отдельный кейс на дополнительной тестовой сделке.

### Числовой оракул для всех кейсов

Сверять отображение с округлением до копеек/центов, а не заменять **фактический** приход расчётным. Формулы из [STAND-TESTPLAN, §2](STAND-TESTPLAN.md#2-эталонные-формулы-по-ним-сверяем-цифры) и `tasks.html` (`brokerSend`, `econ`): пачка 266 000 ₽ → контроль `266 + 40 = 306 ₽`, остаток на рублёвом счёте `532 ₽`, всего удержано `838 ₽`, брокеру `265 162 ₽`, ожидание по `81,40 ₽/USDT` — `3 257,52 USDT`. Для `100 000 ฿` по Coins `31,20 ฿/USDT`: обменная себестоимость `3 205,13 USDT`, валовая прибыль при факте 3 257,52 — `52,39 USDT`. Лизхолд с комиссией компании 1%: Coins нужно `101 000 ฿` = `3 237,18 USDT`, доход компании `1 000 ฿` = `32,05 USDT`, валовая прибыль ≈ `52,39 USDT` (до выплат рефереру). **Фрихолд по новой [спеке](/tmp/freehold-spec.md):** инвойс `X = $45 000`; IPPS банк `S = 45 000 × 1,008 + 50 = 45 410 USDT`, софт-счёт `S = 45 000 × 1,015 + 50 = 45 725 USDT`; курс клиенту `82,4531 ₽/$` даёт `3 710 389,50 ₽`. При прямом приходе 46 000 USDT прибыль банка `590`, софт-счёта `275 USDT` до реферера. **В фрихолде нет THB, Coins, SCB или USDT→THB.** Для прямого прихода `3 300 USDT` и выдачи `100 000 ฿` валовая прибыль обмена `94,87 USDT`. Расхождение менее одного цента из-за порядка округления допустимо только с записью точных полей/API. СБП: от брутто `266 000 ₽` удержание 0,96% = `2 553,60 ₽`, нетто `263 446,40 ₽`; **в сделку идут 266 000 ₽**, не нетто. Допуск рублёвого прихода по умолчанию `1 000 ₽`, курс отклонён >0,5% — предупреждение. В крипто-приходе допуск ±5 USDT. Прибыль CRM сверять с карточкой задачника по *факту* и после партнёрской выплаты.

## P0 · Как проверить уведомления перед включением остальным

**Порядок:** сначала N01 и матрица N02 на **пяти новых сделках K01–K05**, затем N03. Профиль исходящих Telegram — `lk_send_only`: @grusha_lk_bot, разрешён только `sendMessage` в положительный ID личного чата. `getUpdates`, `getWebhookInfo`, отправка документов, группа и иные исходящие запрещены. `STAND_NOTIFY_MODE=karim_only` до отдельного слова Карима. Перед K01 сохранить режим, профиль, Telegram ID и `notify_enabled` из «Сотрудников» и `GET /api/stand/tg-status`; после каждого перехода записывать ID новой заметки.
Привязка по deep link из K00 требует получения апдейтов бота и проверяется отдельно **до** включения `lk_send_only`; в N01–N03 использовать уже записанные Telegram ID в «Сотрудниках». Профиль `lk_send_only` нельзя считать способом привязки.

**Как читать журнал:** `GET /api/stand/tg-status` подтверждает режим и привязки; статус конкретной заметки сверять в «Сотрудниках», если там есть журнал, либо read-only SQL `SELECT note_id, admin_id, status, attempts, at FROM stand_notify_log WHERE note_id=:id ORDER BY admin_id`. На текущем `origin/stage` `tg-status` не отдаёт строки журнала, а `stand_notify_log` хранит статус без причины. Если интерфейс не показывает «подавлено: Марина, менеджер (karim_only)» или эквивалент с именем, ролью и причиной, ставить **FAIL**, не выводить причину из одного режима. Старые `suppressed` после включения не досылать. Для шага без заметки нет новой `note_id` и DM. Считать только новые заметки данной сделки.

## P0 · Новое поступление Сбера появляется на стенде не позже 2 минут

Зеркало читает прод раз в минуту и забирает **окно последних 300** записей `GET /api/sber-incomes`. Использовать только отдельно помеченный тестовый банковский приход; реальную запись клиента не «Забирать». До опыта сверить часы прод/стенд/оператора с UTC. Для протокола записать `uuid`, сумму, `operation_date`, момент первого наблюдения в проде `T_prod` (через прод RO-ключ или Карима) и момент первого появления той же `uuid` в «Поступлениях» задачника `T_stand`; обновлять экран каждые 10–15 с. Приход с устаревшей `operation_date` не годится для позитивного замера.

## Основания и известные точки риска

На срезе T8 `crmPushClose` не обрабатывает `409 requires_confirmation`; это проверяется C02 после T7. `crmPayload` отправляет имена агентов и ищет профиль по имени, что не гарантирует `referrer_id`; это проверяется C04.
- [`app.py`](../app.py): `/api/stand/payin/check` сейчас жёстко TRC-20 (I04); `/api/stand/transfers/check`, `/incoming/check`, `/transfers/demo`; `/api/stand/ref-preview/<id>`; `/api/ref/<token>/payout-request`; `/api/payout-requests/<id>/receipt`; `/api/analytics/dashboard`; ответы 409 `requires_confirmation` при превышении себестоимости. Маршруты `egress-status` и T9/T10 могут появиться только после сведения веток; отсутствие на живом стенде — BLOCKED/FAIL по воротам, не молчаливый PASS.
- [Спецификация фрихолда](/tmp/freehold-spec.md): USD-инвойс, два тарифа IPPS, отсутствие THB/Coins/SCB, MT103 и пропуск курса для крипты. - [`stand_notify.py`](../stand_notify.py) и [`stand_egress.py`](../stand_egress.py): на срезе `origin/stage` бот `grusha_lk_bot` запрещён как прод-имя, профиль `lk_send_only` отсутствует, `_format_note` не добавляет «СТЕНД», а `stand_notify_log` не хранит причину подавления.
