# Фрихолд: блокеры сквозного прогона A

База: `origin/stage` = `9a3c86a`. Ветка: `stand/freehold-e2e-fixes-a`.
Коммит исправлений и тестов: `6d12a9a`.
В `stage` ничего не отправлялось. Живая СД-1484 прочитана через API только для
снимка; переходы, переводы, реквизиты и деньги живой сделки не изменялись.

## Исправления

- **№2, подтверждение сети:** `payout: null` нормализуется в объект до записи
  подтверждённых хэшей и суммы, включая участников пачки. Повторный PUT сохраняет
  серверные поля и тоже переносит `null` без исключения.
- **№3, MT103:** допускается только первое присвоение `paySrc=ipps_swift` на
  переходе s26→s27 у уже существующего маршрута `postConv=ipps_swift`,
  операционистом/администратором, с чеком, фактом оплаты и актуальным подтверждением
  реквизитов. Изменение существующего источника, маршрута или получателя запрещено.
- **№4, закрытие:** панель подтверждений отделена от формы сохранения CRM.
  Операционист получает свою задачу s27 и подтверждение инвойса; менеджер сохраняет
  свои подтверждения и закрытие; администратор видит всю форму. Права API согласованы
  с уже существующими подписями кнопок и `required_role` в ответе проверки закрытия.
- **№6, параллельная конвертация:** разрешён черновик пачки/кошелька операционисту
  и администратору, пока `prepay.brokerStep=s18`, даже после оплаты IPPS. Полный
  переход s18→s18w и приход брокера проверены через API. В исходном коде часть
  проверок уже учитывала `brokerStep`; оставшийся запрет касался `conv` и роли admin.
  Маршрут оплаченного IPPS этим исключением не открывается для редактирования.
- **Неполное старое сетевое подтверждение:** повторная проверка не пропускает
  `confirmed` без `from/to`. Адреса восстанавливаются только из ответа проверки
  сети. Собственный уже записанный payout не считается чужой операцией; занятые
  другой сделкой, приходом или возмещением хэши по-прежнему отклоняются. На s27
  оператору/admin доступна кнопка повторной проверки. Новый ручной ввод хэша
  дополнительно проверен с настоящим верификатором и подменой только сетевого ответа.

Для фрихолда с рублёвым приходом и IPPS:

| Подтверждение | Роль |
| --- | --- |
| Pay-In: проверенный приход | Менеджер |
| Pay-Out: проверенная системой отправка IPPS | Менеджер |
| Оплата инвойса / MT103 | Операционист |
| Чек отправлен клиенту | Менеджер |

Администратор может подтвердить все четыре. Операционист не получает кнопку
сохранения сделки в CRM. Для наличных и несетевой выплаты сохраняется существующее
операторское подтверждение факта.

1. Обычный фрихолд: s14 → приход рублей → реквизиты → брокер → приход USDT →

   Приход 11 000, отправка/возмещение 10 130, прибыль 870 USDT.

   IPPS `TXFqZbXCqoq5QVxRpp9EGLSzkeLMz8iG5D`, **5507.16 USDT**.

   `tests/fixtures/stand_1484_s23_anonymized.json`.

## Ручная приёмка на локальном стенде

1. Создать/использовать локальную копию фрихолда на s14 с приходом рублей.
   Менеджер вносит приход и подтверждает реквизиты; операционист отправляет брокеру.
   После прихода USDT менеджер подтверждает актуальные реквизиты, операционист
   создаёт поручение IPPS. Пройти отправку/подпись мультисига и проверку сети:
   при исходном `payout: null` должен открыться s26 без 500.
2. Операционист прикладывает MT103/чек и завершает s26. Первое `paySrc=ipps_swift`
   не должно давать 409. Попытка поменять оплаченный маршрут по-прежнему запрещена.
3. На s27 под оператором открыть «Текущая задача»: активна «Оплата инвойса»;
   кнопки менеджера неактивны, формы сохранения CRM нет. Под менеджером подтвердить
   Pay-In, Pay-Out, отправку чека и закрыть сделку. Под admin доступны все четыре.
4. На локальной предоплате Теодора сначала завершить отправку IPPS; затем
   операционисту выбрать пачку/кошелёк и отправить брокеру в параллельной ветке.
   После прихода на другой кошелёк выполнить возмещение с хэшем и закрыть сделку.
5. Для локальной копии 1484 на s23 сначала подтвердить реквизиты менеджером,
   затем пройти «Отправил» и найденный перевод 5507.16. Продолжение не требует
   исправлений БД. Не выполнять этот прогон на живой сделке.
6. У старой локальной отправки с подтверждённым хэшем без `from/to` на s27 нажать
   «Повторно проверить перевод в сети». При успешном ответе сети Pay-Out можно
   подтвердить; недоступная сеть/чужой хэш не должны открывать закрытие.

Блокеры №1 (передача менеджером) и №5 (привязка ручного банковского прихода к пачке)
не входят в эту ветку и исправляются отдельно в `stand/freehold-e2e-fixes-b`.
