## Перепроверка 06.09.2026: дефект, внесённый самими исправлениями

Независимая проверка (60 своих сценариев на worktree с `5db0a2a` и на текущем
дереве: 46 из 60 красные до правок, все зелёные после) подтвердила семь групп.
При этом она вскрыла новый дефект в самих правках.

**REG-01 · P1 · Нулевая доля возмещения раздувала прибыль и выплату агентам.**
В `_settle_reimbursement` условие пересчёта прибыли сменилось с
`payin and payout` на `payin is not None`. Сделка, которой в пачке досталась
доля 0 — а так происходит всегда, когда у сделки нет суммы выдачи в батах, —
считала прибыль как «приход минус ноль». На проверке с реферером 30 %:
прибыль 5 → 200 USDT, выплата рефереру 1.50 → 60.00 USDT. До правок прибыль
в этом случае не трогалась вовсе. Путь достижим обычной формой: и пустыми
долями (автораспределение), и предзаполнением пропорцией — сделке без выдачи
форма подставляет ровно `0.00`.

**Исправлено:** прибыль и агенты пересчитываются только при ненулевой доле.
Приход 0 при реальной себестоимости по-прежнему уходит в минус — это была
осознанная часть правки и она сохранена.
**Регрессии:** `test_reimbursement_zero_share_does_not_inflate_profit`
(оба пути формы) и `test_reimbursement_zero_payin_still_gets_negative_profit`
в `tests/test_crash_audit.py`. Обе краснеют на коде без правки.
Ожидание в `test_partial_and_rounded_shares_preserve_every_cent` поправлено:
раньше оно фиксировало как норму именно «прибыль = весь приход» при доле 0.

**Открыто, требует данных прода:** возмещение сделок, у которых вообще нет
суммы выдачи в батах, теперь возвращает 400 «Укажите доли» — раньше проходило
и закрывало их с себестоимостью 0. Насколько это блокирует работу, зависит от
числа таких сделок (`payout_source='founder_personal'`, `reimbursement_id IS NULL`,
`payout_amount_thb` пусто). Посчитать не удалось: read-only ключ CRM в сессии
недоступен, `local.db` данными прода не является.

**Прогоны после правки:** `CALCCRM_TEST_POSTGRES=1 pytest tests/` —
1437 passed, 27 skipped, 6 xfailed, 109 с. Браузер — 21 passed, 6 xfailed.
Фикстура PostgreSQL теперь сама выставляет `LC_ALL=C`: без неё homebrew-кластер
не стартует («postmaster became multithreaded») и три конкурентных сценария
падают с ERROR у любого, кто не держит локаль в окружении.

## DATA-05 · P1 · Частично ручной разнос завышает себестоимость

- **Где:** `app.py:11879`, `_settle_reimbursement`; предварительная проверка
  `app.py:12110` сверяет только сумму явных долей.
- **Триггер:** две pending сделки одного оунера с выдачей по 3000 THB. POST
  `/api/reimbursements`: `amount_usdt=100`, оба ID, `deal_allocations` содержит
  только первую сделку с `amount_usdt=80`.
- **Ожидание:** оставшиеся 20 USDT идут второй сделке либо API атомарно отклоняет
  неполное ручное распределение; общая себестоимость не может быть 130 USDT.
- **Факт:** HTTP 200, в БД доли **80 + 50 = 130**, возмещение — **100**.
  Вторая доля вычисляется от полной суммы, а не остатка после явных долей.
- **Последствие:** завышение расходов и занижение прибыли/реферальных начислений;
  для обеих сделок статус становится completed.
- **Регрессия:** `test_reimbursement_partial_allocations_cannot_exceed_total`.
- **Контрпример:** полностью автоматический разнос 50+50 и полностью ручной
  80+20 проходят `test_reimbursement_full_distribution_preserves_total`.

## DATA-06 · P1 · Повтор возмещения перепривязывает закрытую сделку

- **Где:** `app.py:12143` выборка сделок; `app.py:11893` присвоение
  `deal.reimbursement_id` без проверки существующего возмещения.
- **Триггер:** два последовательных одинаковых POST `/api/reimbursements`:
  один существующий pending deal, сумма 100, оунер «Аудит», без tx-хэшей
  (разрешённый API ручной путь).
- **Ожидание:** идемпотентный ответ с первым ID или 409; один факт возмещения
  и неизменная связь со сделкой.
- **Факт:** оба HTTP 200; сохраняются **две** записи, сделка переключается с
  `reimbursement_id=1` на `2`. Первая запись остаётся без сделок.
- **Последствие:** история и кассовый расход могут учитываться повторно.
  Это доказательство двойной записи, **не** доказательство реального двойного
  блокчейн-перевода. Для повторных одинаковых хэшей существуют отдельные защиты;
  здесь воспроизведён ручной сценарий без хэшей.
- **Регрессия:** `test_reimbursement_repeat_cannot_reassign_settled_deal`.

## Что проверено и не подтвердилось как баг

- При валидном первом и отсутствующем втором приходе конвертация, первая доля
  и резервирование полностью откатываются; баланс не меняется.
- Ошибочная строка курса и невалидный/отсутствующий ID прихода дают 4xx без записи.
- Несуществующая пачка GET/PUT/DELETE и отсутствующий договор при добавлении
  платежа дают JSON 404.
- Отрицательная сумма возмещения отклонена, сделка остаётся pending.
- Искусственный отказ конвертера **на втором PDF** возвращает 500, но договор
  и первый файл полностью откатываются. Замокан только генератор; запись и
  транзакция выполняются реальным SQLAlchemy.

## Ограничения и следующие проверки

1. **PostgreSQL/concurrency:** SQLite не проверяет блокировки `FOR UPDATE`,
   deadlock, несколько gunicorn workers и параллельные операции. Повторное
   возмещение выше ломается уже последовательно, поэтому гонка для него не нужна.
2. **Браузер:** API-воспроизведение не доказывает доступность каждого payload через
   текущую форму. Browser user cases должны отдельно проверять submit, double-click,
   ошибки и перезагрузку страницы. UI-валидация не заменяет контракт серверного API.
3. **Реальные PDF/сервисы:** отказ PDF синтетический; LibreOffice, банковские API,
   Telegram и реальные документы здесь не запускались. Финансовый ущерб реальным
   клиентам не исследован.
4. **Существующий `scripts/qa_sweep.py`:** прочитан, не запущен. Он жёстко направлен
   на `localhost:5055`, ожидает `LOCAL_NO_AUTH`, меняет существующих QA-рефереров
   и некоторые операции индексирует через `['deal']` без проверки ошибки.
   Это не безопасный универсальный runner для произвольной CRM-базы.

Уверенность в локальных воспроизведениях: **90% → 98%** после реального прогона
и проверки записей БД; переносимость на production/PostgreSQL требует отдельного
staging-прогона. Три попытки опровергнуть вывод: полностью ручной/автоматический
разнос, положительная доля с удалением, откат при отказе второго шага — проходят
и ограничивают дефекты конкретными ветками, а не всем модулем целиком.
