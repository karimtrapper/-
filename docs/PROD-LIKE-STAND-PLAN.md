## 1. Решения по умолчанию (согласованы с соведущим, можно менять утром)

1. **Режим «тишина» на время теста.** Стенд не ходит наружу никуда, кроме своей базы и одного закрытого канала в Telegram (п. 2). Курсы, блокчейн-проверки, распознавание документов, чтение прод-API — выключены, на экране честная пометка «на стенде выключено», данные вводятся вручную или кнопкой «Вебхук · демо». Включать любое из них — только после слова Карима, отдельным контрактом и тестом.
2. **Бот уведомлений — @grusha_stand_bot**, не @grusha_lk_bot (прод-токен на стенд не даём). Весь Telegram стенда идёт через одну функцию-канал: она сама проверяет токен стенда, метод (`sendMessage`, `getUpdates`, `getMe`, `getWebhookInfo`) и получателя. Любой другой код, даже `httpx`/`urllib` к `api.telegram.org`, получает отказ на уровне сокета.
3. **Кто может получать.** Функция `can_send(channel, recipient, operation)` — единственная точка решения. Получатель — только положительный числовой ID лички (не группа). Глобальный режим `STAND_NOTIFY_MODE`: `karim_only` (по умолчанию — только аккаунт `karim`, даже если галки стоят у других) → `enabled` (все с галкой «Получает уведомления»), только по команде Карима. Группа `STAND_TG_CHAT` не читается. Ошибка Telegram (403/429/таймаут) — повтор позже, никогда не фолбэк в группу.
4. **Маршрут.** Заметка задачника адресована роли → её получают все включённые сотрудники этой роли (MVP: рассылка по роли, а не персональное назначение). Админ получает копию всех. Дедуп по паре (заметка, получатель) в отдельной таблице, без обрезки «последние 300». Подавленные заметки (режим, галка выключена, не привязан) пишутся как `suppressed` и не досылаются при включении.
5. **Привязка Telegram.** Сотрудник в своём профиле жмёт «Подключить Telegram» → ссылка `t.me/grusha_stand_bot?start=bind_<nonce>` (криптостойкий, 10 минут, одноразовый, привязан к его `admin_id`, атомарный consume). Стенд читает апдейты бота через getUpdates: перед запуском read-only `getWebhookInfo`; если у бота стоит вебхук — getUpdates не запускаем, вебхук не трогаем, статус в UI. Ровно один потребитель: advisory lock в Postgres, offset хранится в базе. Принимаем только private-чат и числовой `from.id`, username не доверяем. Ответ «Подключено» уходит только тем, кому разрешено по п. 3; остальным результат виден только в UI.
6. **Доска задачника после заливки — пустая.** Старая доска уходит в архив (JSON рядом с бэкапом). Историческая CRM (сделки, рефералы, аналитика) и новые задачи на доске — разные вещи, автоматического переноса прошлых сделок в задачи нет.
7. **Аккаунты.** Строки прод-админов остаются (на них ссылаются сделки), но у них `login_disabled = true`: отказ во всех путях входа — пароль, tg-login, tg-poll, поиск по @username. Совпавшие логины переименованы в `prod_<логин>`. Пять логинов стенда заводятся с `STAND_PASSWORD`. Сид больше не перетирает роль, изменённую админом. `SECRET_KEY` стенда при переключении базы меняется: старые cookie с `user_id` не должны попасть в чужой аккаунт.
8. **Всё за логином.** На стенде без сессии открыты только `/login`, `/api/auth/login`, `/api/auth/logout`, `/api/auth/me`, `/api/health` и статика страницы логина. TG-вход, `setup`, вебхуки, `/api/ref/*`, `/api/partner/*`, `/api/kyc/*`, `/api/tg/*`, `X-Api-Key` — закрыты. Кабинет реферала админ открывает из CRM через ручку предпросмотра только для стенда (обычная сессия CRM не равна сессии реферала). Токены ссылок реферала, партнёра, KYC и платёжных ссылок при заливке перевыпускаются.
9. **Прод-справочник агентов.** `STAND_PROD_RO_KEY` и `/api/stand/prod-agents` выключаются: после копии агенты берутся из локальной таблицы `referrers` по id, а не по имени.

## 7. План переезда в прод (только план — выполняет Карим или по его команде)

**Принцип.** Продом становится **код**, а не база стенда. `stage` вливается в `main`, прод-сервис `caring-passion` деплоится из `main` на своей прод-базе; миграции стенда (новые колонки и таблицы) применяются к прод-базе при старте, как все миграции CalcCRM. База стенда (копия прода на момент дампа + тестовые сделки) в прод **не переносится**.

1. **Перед переездом.** Карим принял стенд. Заморозить `stage`. Бэкап прод-базы (`pg_dump` по памяти `reference_railway_api.md`, в `~/Backups/calccrm/`). Проверить на копии прод-базы (одноразовый Postgres из свежего дампа), что старт кода `stage` с `STAND_MODE` не заданным проходит миграции без ошибок: `login_disabled`, `notify_enabled`, `stand_notify_log`, `stand_tg_bind`, `stand_tg_offset`, `sber_incomes`-курсор и т. п. — на проде они создаются, но не используются (всё под `STAND_MODE`).
2. **Что меняется в проде при переезде.** `STAND_MODE` на проде **не задаётся** → выключатель тишины (`stand_egress.install`), gate стенда, RBAC ролей стенда, зеркало Сбера, личка через бота стенда, пометки «на стенде выключено» — всё неактивно; работают прод-интеграции как сейчас. Новое, что реально меняет прод-поведение: `login_disabled` во всех путях входа (у всех прод-админов false — без эффекта), подтверждение расхода выплаты (уже в main), UI-задачник `/tasks` — если он должен стать рабочим инструментом прода, это отдельное решение Карима (сейчас задачник работает только при `STAND_MODE`: `/api/stand/*` → 404 вне стенда).
3. **Решения до переезда (вопросы Кариму).** Задачник в проде — включать ли и с какими ролями (сейчас на проде у всех роль admin). Уведомления задачника в проде (T14) — штатно через @grusha_lk_bot прода (прод и так владеет ботом): назначенному исполнителю, без назначения — роль, админ — копия; отдельный профиль «только отправка» (`STAND_LK_BOT_TOKEN`/`STAND_NOTIFY_PROFILE=lk_send_only`) на проде не нужен — там свой полноценный бот, читает и пишет как обычно. Вопрос «через какой бот» закрыт; открыто только «кому» (какие роли/сотрудники получают уведомления в проде — довключается тем же `admin_users.telegram_user_id`, что и вход). Поступления Сбера для задачника в проде — из той же таблицы `sber_incomes` (ingest уже есть). Какие из стендовых пометок оставить.
4. **Выкат.** PR `stage → main` с полным pytest + node; деплой прод-сервиса; сразу после — `curl` прода: `/api/health`, вход через @grusha_lk_bot, список сделок, создание/закрытие тестовой сделки с пометкой «ТЕСТ» и её удаление, уведомление в рабочую группу, sync в таблицу.
5. **Откат.** Railway: redeploy предыдущего успешного деплоя прод-сервиса (коммит `main` до мержа) — одна кнопка/мутация `deploymentRedeploy`. Новые колонки и таблицы старому коду не мешают (он их не читает), откатывать базу не нужно. Если миграция повредила данные — восстановление из бэкапа шага 1 (с потерей записей после бэкапа, поэтому бэкап — непосредственно перед выкатом). `git revert` мерж-коммита в `main` — чтобы следующий пуш не вернул код.

## 2. Этапы (порядок жёсткий, каждое «ворота» — только PASS)

### Этап 1 — тишина с доказательством (до любых прод-данных) — T1, T2, T7
- **Сеть (T1).** `stand_egress.py`, ставится сразу после блока `STAND_MODE` в `app.py`, до импорта остальных модулей. Патч на уровне `socket.socket.connect`/`connect_ex`, `socket.create_connection`, `getaddrinfo` (покрывает requests, urllib, httpx/OpenAI, aiohttp через `loop.sock_connect`, smtplib, gspread, IP-литералы, IPv6). Разрешено: точный host:port базы из `DATABASE_URL` и loopback. Telegram — только внутри канала п. 1.2 (разрешение через thread-local от функции-канала, отдельная сессия без пула, без редиректов, `trust_env=False`, прокси из env не используются). Нативные пути вне Python-сокетов: libpq (только `DATABASE_URL` стенда) и Chromium Playwright — на стенде Playwright-курсы выключены кодом. `subprocess` с сетью (curl и т. п.) — найти и закрыть. Честная формулировка гарантии — в итоговом отчёте T1.
- **Точки выхода (T1).** Тихий пропуск + лог `[EGRESS-BLOCKED]` без токенов и текста: все `sendMessage`/`sendDocument`/`editMessageText`/`answerCallbackQuery` по боевым токенам, DM рефералам и агентам, Google Sheets (`get_gsheet_client` → None без фолбэка на файл), вебхук завершения, Bitrix (чтение и запись), Doverka, `/api/proxy/create-payment` (403 `stand_blocked`), поллер платёжных ссылок, Реестр WL, Метрика, docparse (403 `stand_blocked`), `deal_chat_analyzer`, TronScan/Etherscan, `stand_transfers.verify_transfer` (default-bound `get`), курсы (`/api/rates` отдаёт «на стенде выключено» или последний ручной курс — T1 выбирает и описывает), transfer-poll (по умолчанию выкл.), `STAND_PROD_RO_KEY`. `PUBLIC_BASE_URL` на стенде = `STAND_BASE_URL`. `Referrer.to_dict` и другие серверные wa.me/t.me на реальных людей → пусто.
- **UI (T7).** `tasks.html`, `crm.html`, кабинет: боевые ссылки брокера и Coins, `CALC_URL` прода, wa.me — на стенде нейтральные. `crmPushClose` понимает ответ `409 requires_confirmation` из прод-кода `d2a8ec6` (подтверждение расхода выплаты) и спрашивает человека, а не падает. Внешние шрифты/CDN/виджет Telegram — не сообщения, отдельный класс; в T7 только описать.
- **Доступ и роли (T2).** Gate перед `PUBLIC_PATHS` (п. 1.8), `login_disabled` во всех путях входа, RBAC: `/api/admins*`, `/api/stand/reset`, `notify_enabled`, `/api/stand/egress-status` — только admin; привязка Telegram — сам себе. Валидация роли, нельзя удалить последнего админа и разжаловать себя. Сид без перетирания. Предпросмотр кабинета реферала для админа. T2 владеет схемой `AdminUser` (`role`, `login_disabled`, `notify_enabled`, `telegram_user_id`) и CRUD аккаунтов.
- **Доказательство.** Каждая проверка — в **свежем subprocess** (conftest сам глушит сеть и подменяет `get_gsheet_client`, внутри pytest-процесса будет ложный зелёный), с импортом и стартом приложения, с боеподобными env и файлом `google_sa.json`. Фейковый внешний сервер (все внешние хосты резолвятся в него) не получает ни одного соединения по всем точкам выхода; фейковый Telegram получает только разрешённые методы стенд-токеном на разрешённый chat_id. Обходы: httpx/urllib/aiohttp к `api.telegram.org`, IP-литерал, IPv6, редирект, `HTTPS_PROXY` в env, `sendDocument`, чужой токен, группа. Негативный контроль `STAND_MODE=0`: guard не установлен, прод-тесты без изменений.
- **Ворота 1:** всё выше PASS у проверяющего другого провайдера + финальный cross-QA соведущего по T1; сведено в `stage`, выкачено; на живом стенде без входа 401 по списку, роль-негатив 403, `egress-status` у админа = active (это телеметрия, не доказательство — доказательство в тестах).

### Этап 4 — копия прод-данных — лидер запускает скрипт T4
Кандидат-база вместо «снести и залить поверх»:
1. Прод: `pg_dump` из libpq 18 с `PGOPTIONS=-c default_transaction_read_only=on`, `--no-owner --no-privileges`, stderr в файл без DSN. Счётчики и денежные агрегаты считаются **из этого же дампа** (restore в одноразовый локальный Postgres), а не из живого API.
2. На сервере `stand-db` создаётся новая база `stand_prodcopy_<дата>`; живой стенд в это время работает на старой базе и кандидата не видит.
3. Restore в кандидата → санация одной транзакцией (`scripts/stand_sanitize.sql`): перевыпуск токенов ссылок, очистка `login_nonces`, `login_disabled` + сброс паролей и `telegram_user_id` прод-админов, `prod_<логин>` при совпадении, `notify_enabled=false` у всех, хранимые в БД вебхуки/чаты → пусто, пустой `stand_state`.
4. Проверка кандидата: таблицы/строки/PK/FK/sequences next id, сделки/агенты/выплаты/договоры/документы/KYC-файлы, суммы прибыли и реферальных начислений = дамп; отличия только в документированных местах (admin_users, токены, nonces, stand_state).
5. Переключение: у `stand-app` меняются `DATABASE_URL` → кандидат и `SECRET_KEY` → новый, `STAND_TG_CHAT`, `STAND_DOCPARSE_KEY`, `STAND_PROD_RO_KEY` удаляются. Redeploy. Если restore или проверка упали — переключения нет, стенд остаётся на старой базе. Откат = вернуть старый `DATABASE_URL`.
6. После старта: сид завёл пять логинов, `karim` — `notify_enabled`; живые проверки ворот 1 повторяются. Прокси `stand-db` снимается.

**Интерфейсы (фиксируем до старта):**
- `stand_egress.install()`, `stand_egress.status()`, `stand_egress.tg_call(method, payload) -> dict` — единственный путь в Telegram; внутри вызывает `stand_egress.can_send('telegram', chat_id, method)`, которая спрашивает зарегистрированную политику `stand_egress.set_policy(callable(channel, recipient, operation) -> bool)`; по умолчанию политика отвечает False на всё, кроме `getMe`/`getWebhookInfo`/`getUpdates`.
- T5 регистрирует политику: `sendMessage` разрешён на chat_id ∈ {`telegram_user_id` аккаунтов, разрешённых режимом `STAND_NOTIFY_MODE` и галкой}.
- Колонки `AdminUser`: `login_disabled` (bool, default false), `notify_enabled` (bool, default false), миграции идемпотентны. Создаёт T2; T4 и T5 рассчитывают на эти имена.

## 4. Критерии приёмки

Безопасность и деньги — только PASS. `open` или FAIL по ним блокирует следующий этап.

1. Тишина: тесты в свежем subprocess при боеподобных env — 0 соединений с внешним фейк-сервером по всем точкам выхода и обходам; фейковый Telegram получил только разрешённое. `STAND_MODE=0` — поведение прода не изменилось.
2. Живой стенд до заливки: без входа 401 на `/api/stand/state`, `/api/ref/*`, `/api/partner/*`, `/api/kyc/*`, `/api/tg/*`, `/api/rates`, вебхуки; менеджер не меняет роль (403); прод-аккаунт с `login_disabled` не входит ни одним путём.
3. Бэкап стенда: файл, SHA256, проверочный restore прошёл, путь назван Кариму.
4. Кандидат-база: числа и денежные суммы = дамп прода; отличия только документированные.
5. Прод не тронут: деплоев прода после начала работы нет, `main` не пушился, дамп снят в read-only транзакции.
6. Разрешённая отправка отделена от запрещённых: тестовое уведомление приходит Кариму в личку от @grusha_stand_bot; в группу и другим людям — ничего, пока режим `karim_only`.
