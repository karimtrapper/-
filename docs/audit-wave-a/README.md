## Архитектурные решения

- Правила графа, валютных пар и обработки журнала вынесены в небольшой `stand_workflow.py`. Проверка выполняется в существующем транзакционном PUT после проверки роли, до записи. Для прошлого журнала сохранена совместимость со строками и отсутствующим `at`.
- Исторические записи и новые человеческие комментарии разделены по происхождению. Новые служебные уведомления формирует `_stand_state_events`, а доставка использует прежний механизм `stand_notify`; браузер сопоставляет возвращённый серверный ID с окном результата.
- Техническая нормализация не мигрирует всю старую доску и не игнорирует произвольные изменения: удаляет из предложения только известные отсутствующие defaults, с точным совпадением типа и значения.
- Для THB-входа и USDT/RUB-выхода использованы уже существующие валютные поля CRM `custom_*`, без миграции схемы. Это представление в CRM не превращает исходную заявку в ручную: сервер сам выводит допустимый формат из сохранённой пары, сверяет суммы и сохраняет проверки provenance/хешей.
- Документы используют правильную пару, а не прежний RUB_THB по умолчанию. THB→RUB хранит в документе обратный курс THB/RUB; клиентский курс остаётся RUB/THB. Для выдачи USDT добавлены поля сети и кошелька получателя. Исторические документы не переписываются.
- Общий каталог инициализируется при создании/сбросе, без перезаписи пользовательского справочника существующей доски и без добавления несуществующих записей только в GET-проекцию.
- Фактический счёт ручного прихода хранится отдельно от счёта выпущенного договора. Несовпадение протоколируется, исходные реквизиты документа не меняются. Подтверждение Сбер API не заменено ручным подтверждением.
