# Решения по целостности денежных операций

## 2026-09-06 — Возмещения и резервирование конвертаций

**Контекст:** аудит воспроизвёл завышение долей возмещения, повторное закрытие
сделки и увеличение остатка отрицательной долей. Исходный код: `5db0a2a`.

**Решили:**

- Возмещение и ручные доли имеют точность до цента. Остаток после ручных долей
  распределяется только между неуказанными сделками пропорционально выдаче.
  Округление — метод наибольших остатков, равенство разрешается по меньшему ID.
  Полностью ручное распределение обязано совпадать с суммой возмещения.
- При отсутствии сумм выдачи требуется явное распределение: равные доли
  не подставляются автоматически, поскольку их экономическое основание неизвестно.
- Повторное возмещение уже связанной сделки возвращает 409. Завершённая сделка
  без предыдущего возмещения остаётся допустимой для существующего сценария
  возврата фаундеру. Все выбранные ID должны существовать до первой записи.
- Проверка состояния, резервирование и финансовые записи выполняются в одной
  транзакции. PostgreSQL блокирует сделки и существующие переводы через
  `FOR UPDATE` в определённом порядке; автозачёт использует ту же защиту.
- В конвертации отрицательные/неконечные суммы запрещены и с `force`.
  Существующий `force` сохраняет явное разрешение положительного перебора;
  нулевая/неуказанная доля сохраняет значение «взять свободный остаток».
- Проверки конкуренции запускаются на одноразовом локальном PostgreSQL
  (`CALCCRM_TEST_POSTGRES=1`), без подключения к `DATABASE_URL` пользователя.

**Почему:** сохраняем сумму операции, не создаём повторный расход при повторе
запроса и проверяем межтранзакционные блокировки на PostgreSQL.

**Отвергли:** защиту только кнопкой/локом Python (не покрывает независимые
запросы); молчаливое переприсвоение возмещения; пропорцию от полной суммы
после ручных долей; немедленную миграцию всех денежных Float-колонок на Numeric
(отдельная задача с анализом исторических данных и миграцией).

**Границы:** исправление кода не исправляет историю автоматически. Перед
выпуском необходимы резервная копия и сверка production; доступ Railway
в текущей сессии пока не восстановлен. Гарантия отсутствия дубля относится
к финансовой записи CRM, а не к отправке блокчейн-транзакции.
